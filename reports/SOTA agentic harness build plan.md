# Wrap a Thin Agent Loop in Thick Controls

As of November 2026, the state-of-the-art agentic harness is a deliberately thin, model-native loop (sample the model, execute tool calls, append results, repeat until the model stops calling tools and no queued input or evaluator objects) wrapped in a thick, configurable control plane that does most of the measurable work. Anthropic, OpenAI and the leading open-source projects have converged on the same components around that loop: a durable append-only session log kept outside the context window; a cache-stable prompt layout with a graded compaction ladder; file-based memory with background consolidation; a small bash-plus-filesystem tool kernel extended through deferred tool search, MCP, Agent Skills and AGENTS.md; an OS sandbox behind a default-deny egress proxy; a layered permission pipeline that ends in a model classifier; code-driven multi-agent fan-out that always ends in a verifier; and an eval-and-trace flywheel. The stakes are concrete: with the model held fixed, harness changes alone reportedly lifted LangChain's coding agent from **52.8% to 66.5% on Terminal-Bench 2.0** ([explainx.ai summary](https://www.explainx.ai/blog/agent-harness-engineering-terminal-bench-langchain-2026)), and Claude Opus 4.5 scored **20.5% higher inside the Claude Code SDK** than in a generalist scaffold ([AgencyBench](https://arxiv.org/pdf/2601.11044)). Because frontier models are post-trained inside their vendors' harnesses, matching native tool formats and reasoning-replay rules is worth points on its own. The same evidence carries the warning that shapes the whole plan: every harness component encodes an assumption about what the model cannot do alone, and labs keep deleting scaffolds such as context resets, sprints and todo tools as models improve ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)), so every component below should ship behind a flag and survive only while evals prove it load-bearing. The recommended build order is evals and a baseline first, then the core loop and sandbox, context and caching, permissions, extensions, long-horizon control, memory, multi-agent orchestration, production hardening, and finally automated harness optimization and RL on your own environments.

*Source note: openai.com, developers.openai.com, arxiv.org, tbench.ai and several other hosts were unreachable during research, so figures that came only through search summaries or secondary write-ups are marked "reported" or "secondary". Primary code (the `openai/codex` repository at `main`, Anthropic's SDKs and documentation) was read directly.*

## Architecture: a session log, a harness and a sandbox, each replaceable

The cleanest statement of the target architecture is Anthropic's Managed Agents design (April 8, 2026), which splits an agent into three independently swappable interfaces: a **session** that is "an append-only event log," a **harness** that is "the loop that calls Claude and routes Claude's tool calls," and a **sandbox** that executes them ([Anthropic](https://anthropic.com/engineering/managed-agents)). Tools dispatch through `execute(name, input) → string`, sandboxes are created with `provision({resources})`, events persist via `emitEvent(id, event)`, and `getEvents()` returns positional slices so the harness can rewind or re-read history. When a harness process crashes, a replacement calls `wake(sessionId)` and `getSession(id)` and resumes "from the last event"; when a sandbox dies, the failure returns to the model as a tool error it can retry. The first design kept all three in one container, so a container failure lost the session; decoupling made containers disposable, and provisioning them lazily (only when a tool call needs one) cut **p50 time-to-first-token by about 60% and p95 by more than 90%**, a gain that came entirely from harness architecture. The log lives outside the context window for a principled reason: compaction, memory writes and trimming of old tool results or thinking blocks are irreversible, so the model-visible context must be a *projection* of a log that is never destroyed.

Open-source harnesses implement the same split. The OpenHands Software Agent SDK stores the conversation as an append-only event log, records condensation as `Condensation` events "similar to tombstones in … Cassandra and Kafka," and computes the LLM-visible `View` by applying them ([OpenHands condenser README](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/README.md)). Cline's SDK keeps the canonical history at full fidelity, stores compaction state separately in `${sessionId}.compaction.json` that is reused on resume only after validating a hash of the canonical prefix, and separates a "stateless runtime loop" package (`@cline/agents`) from a stateful core that owns sessions, persistence and compaction policy ([Cline ARCHITECTURE.md](https://github.com/cline/cline/blob/main/sdk/ARCHITECTURE.md)). Codex persists sessions as append-only JSONL rollouts (`session_meta`, `turn_context`, `event_msg`, `response_item`) that double as evidence for its memory pipeline ([Codex read_path.md](https://github.com/openai/codex/blob/main/codex-rs/ext/memories/templates/memories/read_path.md)). A builder should copy this pattern exactly: an immutable event store, a context projector that builds each request from it, and compaction recorded as an event rather than as a destructive rewrite.

The loop itself should be thin. mini-swe-agent is "just some 100 lines of python" for the agent class, uses no tool except bash, does not even use the tool-calling interface, keeps "a completely linear history," and runs every action as an independent `subprocess.run`, yet it scores **above 74% on SWE-bench Verified** ([mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent)); on Vals.ai's independent runs the top three SWE-bench Verified entries in September 2026 (Claude Opus 5 at 97.00%, DeepSeek V4 Pro at 96.40%, GPT-5.6 Sol at 96.20%) all used this bash-only harness ([Vals.ai](https://www.vals.ai/benchmarks/swebench), secondary summary). Pi, among the most-starred harnesses at about 119.6k stars, ships exactly four coding tools (`read`, `bash`, `edit`, `write`) and deliberately skips subagents and plan mode ([Pi tools](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/src/core/tools/index.ts); [Pi README](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/README.md)). The measured gains come from what wraps such cores: LangChain's +13.7 points came from time-budget warnings and loop-detection middleware that counts edits per file ([explainx.ai](https://www.explainx.ai/blog/agent-harness-engineering-terminal-bench-langchain-2026), secondary), and Codex CLI with GPT-5.5 reportedly beats the neutral Terminus 2 harness by 5.2 points on Terminal-Bench 2.1 ([Daniel Vaughan](https://codex.danielvaughan.com/2026/06/11/terminal-bench-2-1-june-2026-benchmark-landscape-codex-cli-harness-engineering-model-scores/), secondary). Anthropic's 2024 vocabulary still frames the design space (workflows run "through predefined code paths," agents "dynamically direct their own processes," and the advice is to "find the simplest solution possible") ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)), but in 2026 practice the workflow patterns (routing, plan gates, evaluator gates, orchestrators) are composable outer structure around one autonomous loop, not alternatives to it.

The client boundary deserves a deliberate choice because it determines who can embed the harness, and three shapes dominate. Codex's app-server speaks JSON-RPC over a thread/turn/item model (`thread/start|resume|fork|compact/start`, `thread/goal/set`, `turn/start`, `turn/steer`, `turn/interrupt`, streamed `item/agentMessage/delta`, and item-level approval requests such as `item/commandExecution/requestApproval`), and every OpenAI surface is built on it ([app-server-protocol](https://github.com/openai/codex/tree/main/codex-rs/app-server-protocol)); its headless `codex exec --json` emits JSONL `thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.*` and `error` events ([exec_events.rs](https://github.com/openai/codex/blob/main/codex-rs/exec/src/exec_events.rs)). The Claude Agent SDK treats the harness as a subprocess and exchanges newline-delimited JSON with `control_request` subtypes `initialize`, `can_use_tool`, `hook_callback` and `mcp_message`, so the host supplies permissions, hooks and in-process MCP tools ([claude-agent-sdk-python query.py](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/_internal/query.py)). The Agent Client Protocol (ACP) is spoken by Kimi Code, Goose, deepagents and Pi, and lets OpenHands' Agent Canvas drive any of them ([OpenHands README](https://github.com/OpenHands/OpenHands/blob/main/README.md)). The pragmatic choice is to expose a JSONL headless mode plus an ACP server, model the internal API on app-server thread/turn/item semantics, and make the model layer a provider adapter with a configurable base URL and model-alias map. DeepSeek's Anthropic-compatible endpoint (`https://api.deepseek.com/anthropic`, which ignores `anthropic-beta` headers and maps Claude model names onto V4 models) shows how cheaply that buys portability ([DeepSeek docs](https://api-docs.deepseek.com/guides/anthropic_api), via search summary).

## The loop: stop only when tools, queued input and evaluators agree

Every major harness runs the same inner loop, and the details that matter are termination and error semantics. The Claude Agent SDK "runs the same execution loop that powers Claude Code": it sends the prompt with system prompt, tool definitions and history, lets Claude return text, tool calls or both, executes tools through hooks that can "intercept, modify, or block" them, repeats "until it produces a response with no tool calls," and ends with a `ResultMessage` carrying final text, usage, cost and `session_id` ([Claude Code docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)). Codex's `run_turn` computes `needs_follow_up = model_needs_follow_up || has_pending_input` (tool calls *or* user input queued mid-turn), may compact mid-turn, and when no follow-up is needed runs Stop hooks that can block with a continuation prompt recorded as a new message before the loop continues ([turn.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn.rs)). The OpenAI Agents SDK `Runner` classifies each output as a final output (end), a handoff (switch agent and rerun) or tool calls (execute, append, rerun) ([running_agents.md](https://github.com/openai/openai-agents-python/blob/main/docs/running_agents.md)). The canonical predicate is therefore: **stop only when the last response has no tool calls, no user input is pending, and every Stop hook or goal evaluator allows it.**

```text
loop:
  resp = sample(project(log), tools, reasoning_cfg)   # streamed; transient errors retried with backoff
  log.append(resp)                                    # keep reasoning items / thinking signatures verbatim
  if resp.tool_calls:
      results = run(resp.tool_calls)                  # read-only calls in parallel, mutating calls in sequence,
      log.append(results)                             # all through the permission pipeline; native tool-result role
  pending = drain_steering_queue()
  if over_compaction_threshold() and (resp.tool_calls or pending): compact(); continue
  if not resp.tool_calls and not pending:
      verdict = stop_hooks_and_goal_evaluator(log)
      if verdict.block and verdict.prompt: log.append(verdict.prompt); continue
      break
  enforce budgets (turns; dollars checked post-response; wall clock); run stuck and loop detectors
```

Budgets and termination reasons should be first-class. In the Claude SDK a turn is one model output plus tool execution; `max_turns` counts each tool-calling turn plus the final text-only response, `max_budget_usd` caps estimated spend, both default to no limit, and the docs say "Setting a budget is a good default for production agents" ([agent loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)). Because spend is checked after each response, it can overshoot by one response plus running subagents; at the cap, subagent spawns fail with `Budget limit reached` and background subagents stop. The termination enum is worth copying verbatim: `ResultMessage.subtype` is `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution` or `error_max_structured_output_retries`, each carrying `total_cost_usd`, `usage`, `num_turns` and `session_id`, with a separate `stop_reason` of `end_turn`, `max_tokens` or `refusal` (null after a crash). The Agents SDK adds `error_handlers` for `"max_turns"`, `"model_refusal"` and `"invalid_final_output"` that return fallback outputs instead of raising, and `tool_not_found_behavior="return_error_to_model"` so a hallucinated tool name becomes a correctable error ([running_agents.md](https://github.com/openai/openai-agents-python/blob/main/docs/running_agents.md)).

| Error class | Examples | Harness action | Source |
|---|---|---|---|
| Transient | Dropped stream, overload, 5xx, idle stream | Retry with backoff: Codex `DEFAULT_STREAM_MAX_RETRIES = 5`, `DEFAULT_REQUEST_MAX_RETRIES = 4`, `DEFAULT_STREAM_IDLE_TIMEOUT_MS = 300_000`; `/goal` pauses after three retries | [Codex lib.rs](https://github.com/openai/codex/blob/main/codex-rs/model-provider-info/src/lib.rs); [/goal](https://code.claude.com/docs/en/goal) |
| Rate or usage limit | 429, plan usage exhausted | Pause and resume at reset; Codex returns `UsageLimitReached` without retry | [turn.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn.rs) |
| Terminal | Auth failure, exhausted credit, unavailable model, `SessionBudgetExceeded`, `Fatal` | Stop, clear any goal, surface to the user | [/goal](https://code.claude.com/docs/en/goal) |
| Context overflow | `ContextWindowExceeded`, `model_context_window_exceeded` | Compact; if compaction cannot clear it, terminate (Claude Code stops auto-compacting "after a few attempts" rather than looping) | [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works) |
| Tool failure | Sandbox died, command failed, call denied | Return as the tool result so the model adapts; never crash the loop | [Managed Agents](https://anthropic.com/engineering/managed-agents) |

Concurrency and steering follow simple rules. "Read-only tools (like `Read`, `Glob`, `Grep`, and MCP tools marked as read-only) can run concurrently. Tools that modify state (like `Edit`, `Write`, and `Bash`) run sequentially," and custom tools default to sequential unless they set `readOnlyHint` ([agent loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)). Users steer through a queue: in Claude Code, Esc cancels the running tool call, while a correction typed without stopping is read "as soon as those calls finish, within the same turn" ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). Codex exposes the same capability as `turn/steer` and `turn/interrupt`, and gives the model loop-control tools: `get_context_remaining`, `new_context` (which "does not clear, reset, or otherwise affect environment state") and a `sleep` that "ends early when new input arrives" ([Codex handlers](https://github.com/openai/codex/tree/main/codex-rs/core/src/tools/handlers)).

Hooks turn the thin loop into a controllable one, and the vocabulary has standardized. Claude Code and Codex share `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStop`, `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreCompact`, `PostCompact` and `PermissionRequest` ([Claude Code hooks](https://code.claude.com/docs/en/hooks); [Codex hooks](https://github.com/openai/codex/tree/main/codex-rs/hooks/src)), and Claude Code adds many more, including `PostToolBatch`, `TaskCompleted`, `TeammateIdle`, `FileChanged`, `WorktreeCreate`, `PreModelSwitch` and `Elicitation`. Hook types are `command`, `http` and `mcp_tool` (600-second default timeout), `prompt` (a single-turn LLM decision, 30 s) and `agent` (a tool-using subagent of up to 50 turns, 60 s). Exit code 2 blocks with stderr as the reason; `PreToolUse` returns `permissionDecision` of `allow`, `deny`, `ask` or `defer` plus an optional `updatedInput` that rewrites arguments; a Stop hook returns `{"decision":"block","reason":…}` to force continuation or `{"continue": false}` to halt; and hooks "don't consume context." Gemini CLI uses different names but adds model-level events (`BeforeModel`, `AfterModel`, `BeforeToolSelection`) worth adopting ([Gemini CLI hook types](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/hooks/types.ts)). Implementing the Claude/Codex names and JSON semantics buys immediate compatibility with an existing ecosystem of hooks and plugins.

Reasoning state must be replayed correctly inside tool loops, and each vendor has a different non-negotiable rule. On Claude, adaptive thinking (`thinking: {type: "adaptive"}`) interleaves reasoning between tool calls; manual `budget_tokens` is deprecated and "Claude 4.7 and later models… reject requests that use it, returning a 400 error," with depth set instead by `output_config: {effort}` (`low`, `medium`, `high`, `xhigh`, `max`; Opus 5.5 and Haiku 5.5 default to medium, other models to high) ([Extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)). Opus 4.5 and models 4.6+ keep prior thinking blocks in context billed as input, thinking blocks paired with tool results must be returned unmodified with signatures, and changing thinking settings invalidates cache breakpoints, so "pick a budget and hold it stable." On OpenAI, Codex sends `store: false` with `include: ["reasoning.encrypted_content"]` and replays encrypted reasoning items itself ([client.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/client.rs)); the bundled GPT-6 migration guide changes effort mid-conversation by adding a `configuration_update` input item while keeping request-level `reasoning.effort` unchanged "to preserve the prompt prefix for caching" ([upgrading-to-gpt-6-astra.md](https://github.com/openai/codex/blob/main/codex-rs/skills/src/assets/samples/openai-docs/references/upgrading-to-gpt-6-astra.md)), and the Agents SDK's `reasoning_item_id_policy="omit"` avoids 400 errors from orphaned reasoning items. DeepSeek V3.2 keeps reasoning across tool calls and discards it only when a new user message arrives; in tool loops `reasoning_content` must be passed back or the API returns 400, and frameworks that simulate tool results as user messages (the report names Roo Code and Terminus) trigger the discard ([DeepSeek-V3.2 report](https://arxiv.org/pdf/2512.02556), via search snippet; [DeepSeek thinking mode](https://api-docs.deepseek.com/guides/thinking_mode/)). The harness rule: tool results always return in the native tool-result role, and the reasoning configuration is part of the cache key.

Explicit planning has shifted from a crutch for the model to an interface for the user. Native interleaved thinking makes the 2025 "think" tool, which lifted τ-bench airline pass^1 from 0.370 to 0.570 ([Anthropic](https://www.anthropic.com/engineering/claude-think-tool)), largely redundant, and Claude Code now enables `TodoWrite`/`Task*` tools by default only on Opus 4.7, Sonnet 4.6, Haiku 4.5 and earlier because "newer models track multi-step work without a written todo list" (opt in with `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`) ([Track todos](https://code.claude.com/docs/en/agent-sdk/todo-tracking)). Codex keeps `update_plan` with one-sentence steps of 5–7 words, statuses `pending`/`in_progress`/`completed`, and "exactly one `in_progress` step until everything is done" ([default.md](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)). Both harnesses separate a plan *tool* from a plan *mode*: Codex Plan Mode permits only non-mutating actions, errors on `update_plan`, and ends in a "decision complete" `<proposed_plan>` another agent can implement ([plan.md](https://github.com/openai/codex/blob/main/codex-rs/collaboration-mode-templates/templates/plan.md)). Codex's base prompt also encodes autonomy ("keep going until the query is completely resolved… Only terminate your turn when you are sure that the problem is solved") plus a short preamble before grouped tool calls, and OpenAI's 2026 guidance warns that newer models are "more likely to ask the user a question" and stop early, so prompts should say "persist until the user's intended goal is complete" ([prompting-guide.md](https://github.com/openai/codex/blob/main/codex-rs/skills/src/assets/samples/openai-docs/references/prompting-guide.md)).

Runaway protection belongs in harness code. Claude Code stops auto-compacting "after a few attempts" when one huge output refills the window ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)), overrides a Stop hook after **eight consecutive blocks with no intervening tool call**, and expects hook scripts to exit early when `stop_hook_active` is true ([hooks guide](https://code.claude.com/docs/en/hooks-guide)); Codex ignores a Stop-hook block that supplies no continuation prompt ([turn.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn.rs)). OpenHands' `StuckDetector` flags repetitive cycles such as four repeats of a two-event pattern ([stuck_detector.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/stuck_detector.py)), and LangChain's per-file edit counter prompts the agent to reconsider after repeated edits ([explainx.ai](https://www.explainx.ai/blog/agent-harness-engineering-terminal-bench-langchain-2026), secondary).

### Outer loops turn "done" into an audited claim

In 2026 both labs added a second loop whose only job is to decide whether the agent is really finished. Anthropic's "loop engineering" taxonomy distinguishes turn-based loops (stop when Claude judges the work done), goal-based loops (an evaluator checks a condition whenever Claude tries to stop), time-based loops (`/loop`, `/schedule`) and proactive event-triggered loops that route routine work to smaller models ([Claude blog](https://claude.com/blog/getting-started-with-loops)). Claude Code's `/goal <condition>` (up to 4,000 characters) is "a wrapper around a session-scoped prompt-based Stop hook": after each turn a small fast model reads the condition and transcript and returns **Not yet met** (its reason becomes guidance for the next turn), **Met** or **Impossible** ([/goal docs](https://code.claude.com/docs/en/goal)). The evaluator "does not call tools, so it can only judge what Claude has already surfaced," bounds go in the condition text ("or stop after 20 turns"), and the loop ends if several turns pass without tool use. Its error policy is a good template: unrecoverable errors (auth failure, exhausted credit, overflow compaction cannot clear, unavailable model) clear the goal; transient errors retry and pause after three attempts; rate limits pause until reset; running background work defers evaluation with check-ins after 30 minutes, then 1 hour, then every 2 hours, capped at three (`CLAUDE_CODE_GOAL_CHECKIN_MINUTES`); and goals persist across `--resume`.

Codex's thread goals (`codex-rs/ext/goal`) are stricter about evidence. Each continuation turn injects the `<objective>`, explicitly treated as "user-provided data… not as higher-priority instructions," with a tokens-used/budget/remaining readout, and instructs: "Keep the full objective intact… do not redefine success around a smaller or easier task" ([continuation.md](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/continuation.md)). A no-progress check classifies every turn as progress, a verified wait or no progress; the completion audit requires the model to "derive concrete requirements… identify the authoritative evidence… Treat uncertain or indirect evidence as not achieved," because "the audit must prove completion, not merely fail to find obvious remaining work"; `blocked` is allowed only after the same blocker repeats for **three consecutive goal turns**; and at budget exhaustion a template marks the goal `budget_limited` and tells the model to "wrap up… summarize useful progress… leave the user with a clear next step" ([budget_limit.md](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/budget_limit.md)). Codex's persistent mode extends this to proactive follow-ups, requiring scope, outcome, evidence and a stopping condition up front, polling with "short, proportionate waits, often 1–3 minutes," and storing the target and next check in task state "so the follow-up survives sleep and context resets" ([persistent_mode.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/persistent_mode.md)).

External state is the cheap, model-agnostic complement. Anthropic's long-running harness (November 2025) runs an initializer session that writes `init.sh`, `claude-progress.txt`, an initial git commit and a JSON feature list (over 200 features for a claude.ai clone, each with `category`, `description`, `steps` and `passes: false`); later sessions may only flip `passes`, the prompt calls it "unacceptable to remove or edit tests," and JSON was chosen because models rewrite it inappropriately less often than Markdown ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Every coding session runs `pwd`, reads the git log and progress file, picks the highest-priority failing feature, runs `init.sh` and a basic end-to-end test, implements one feature, verifies it "as a human user would" with Puppeteer MCP, then commits and updates progress; the post concludes that "compaction isn't sufficient" for multi-window work. The open quickstart `claude-quickstarts/autonomous-coding` adds defense in depth with an OS sandbox, a project-restricted filesystem and a bash allowlist enforced by a security hook ([quickstart README](https://github.com/anthropics/claude-quickstarts/blob/main/autonomous-coding/README.md)), which illustrates the general rule that invariants like "never delete tests" belong in hooks, not prompts.

Evaluator separation is the strongest lever for long runs. Anthropic's planner → generator → evaluator harness uses "sprint contracts" in which generator and evaluator agree in files on what "done" means before coding, and an evaluator that drives the running app with Playwright MCP against hard per-criterion thresholds; "tuning a standalone evaluator to be skeptical" proved easier than making a generator self-critical ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). On Opus 4.5 a solo run took **20 minutes and $9 and produced a broken game**, while the full harness took **6 hours and $200 and produced a playable one**. On Opus 4.6 the sprints were removed and the evaluator became a single end-of-run pass; a browser DAW build took about 3 h 50 min and $124.70, with the builder running "coherently for over two hours without sprints." Sonnet 4.5 had shown "context anxiety," wrapping up early near its perceived limit, which made fresh-context resets essential until Opus 4.5 removed the behavior and resets became "dead weight" ([Managed Agents](https://anthropic.com/engineering/managed-agents)). The Ralph loop is the extreme outer loop: Anthropic's official plugin runs `/ralph-loop "<prompt>" --max-iterations <n> --completion-promise "<text>"`, with a Stop hook that re-feeds the same prompt until the last assistant message contains `<promise>…</promise>` and state in `.claude/ralph-loop.local.md` ([ralph-loop plugin](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop)). Models are meeting harnesses halfway: GPT-5.1-Codex-Max was "trained to run across several context windows via compaction" and worked more than 24 hours in internal evaluations ([OpenAI](https://openai.com/index/gpt-5-1-codex-max/), search snippet), and METR puts Claude Mythos Preview's 50% time horizon at 16 hours or more (95% CI 8.5–55 h) while warning its suite is near saturation ([METR](https://metr.org/blog/2026-01-29-time-horizon-1-1/), via search summary).

The implementation consequence is to ship three continuity mechanisms, each flagged per model: in-loop compaction near 90% of the window with a handoff-style summary and the durable log behind it; an optional `new_context`-style reset bootstrapped from progress files for models that show context anxiety; and an outer goal loop with an independent evaluator, no-progress detection, a blocked-after-three rule, token and wall-clock budgets, and pause, retry and clear semantics per error class.

## Context: every token is a cost, a cache key and a distraction

Anthropic's guidance, now built into the Claude docs, is to find "the smallest set of high-signal tokens that maximizes the likelihood of the desired outcome" ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). The case rests on context rot: Chroma's 2025 study of 18 models found performance "grows increasingly unreliable as input length grows" even on trivial tasks; focused inputs of about 300 tokens beat ~113k-token full histories containing the same answer on LongMemEval prompts; and plausible distractors, low needle–question similarity and logically coherent haystacks all worsened the decline ([Chroma](https://research.trychroma.com/context-rot), via search extract; [ZenML summary](https://www.zenml.io/llmops-database/context-rot-evaluating-llm-performance-degradation-with-increasing-input-tokens)). Anthropic calls the decline a gradient rather than a cliff that bigger windows will not remove, and the docs stress that everything counts toward the window, including tool definitions and thinking, and that cached prefixes still occupy space because caching changes price, not size ([Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)). The practical rules are to write system prompts at the "right altitude" between brittle if/else logic and vague guidance, starting minimal and adding instructions only for observed failures; keep tools few and non-overlapping; use a handful of canonical examples instead of edge-case lists; and keep lightweight identifiers (paths, queries, URLs) in context while loading data just in time with grep, glob, `head` and `tail`. Claude Code's hybrid (CLAUDE.md pre-loaded, everything else fetched on demand) is the default for code, and the Agent SDK post recommends agentic search first, "only adding semantic search if you need faster results" ([Claude blog](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)).

### Cache stability is the first-order cost constraint

Agents are input-dominated: Manus reports an input:output ratio around **100:1** over roughly 50 tool calls per task, with cached Claude Sonnet input at $0.30/MTok versus $3 uncached, and calls KV-cache hit rate "the single most important metric for a production-stage AI agent" ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus), via search).

| Provider | Mechanism | Key numbers | Gotchas |
|---|---|---|---|
| Anthropic | Up to 4 explicit `cache_control` breakpoints, or one automatic top-level breakpoint; prefix order `tools → system → messages` | Reads 0.1× base input (0.05× on Opus/Sonnet 5.5; 0.025× on Fable/Mythos 5.1); writes 1.25× (5-min TTL) or 2× (1-hour); minimum cacheable 512 tokens on 5.5-generation models, up to 4,096 on Opus 4.5/4.6 | Reads look back only 20 blocks; TTL counts from request start; an entry exists only once the first response starts; tool changes invalidate everything; `tool_choice`, images, thinking and effort invalidate messages ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)) |
| OpenAI | Automatic for prompts ≥1,024 tokens; `prompt_cache_key`; `prompt_cache_retention` of `in_memory` or `24h` | Up to 90% lower input cost and 80% lower latency; keep each prefix+key under ~15 requests/minute | GPT-5.6+ reportedly requires `prompt_cache_key`, guarantees ≥30-minute retention and adds explicit breakpoints; 24h retention is not ZDR-eligible ([OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching), via search) |
| DeepSeek | Automatic disk caching with hit/miss tokens in usage | V4 Flash reportedly $0.0028/MTok hit vs $0.14 miss ([benchlm](https://www.benchlm.ai/deepseek/api-pricing), secondary) | A hit needs the prefix already persisted to disk ([DeepSeek](https://api-docs.deepseek.com/guides/kv_cache), via search) |

The layout rule follows: serialize tools (stable, mostly deferred), then system prompt, then project instructions and skill index, then an append-only conversation, with breakpoints at the end of tools, at the end of system and project context, at the moving tail, and an extra mid-history breakpoint whenever one turn can add 20+ blocks. Never put timestamps, environment state or budgets in the prefix; a breakpoint on a block containing a timestamp means "a write every request and never a read" ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). Claude's late-2026 features make dynamic content cache-safe: append `{"role":"system"}` messages mid-conversation instead of editing top-level `system`; add, change or withdraw tools with `tool_addition`/`tool_removal` blocks (beta `inline-tools-2026-09-15`) so the `tools` array stays byte-identical; and use **turn-scoped system messages** (beta `mid-conversation-system-clear-at-2026-08-21`, `clear_at: "next_user_message"`) that render until the next user or tool-result message and then cost zero tokens, which cleanly resolves the tension between Manus-style recitation and cache stability ([Mid-conversation system messages](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)). Deferred tools found by search are appended inline as `tool_reference` blocks, leaving the prefix untouched ([Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)); on self-hosted models, Manus's alternative is to keep definitions fixed and mask logits, using shared prefixes such as `browser_*` and `shell_*` to constrain whole groups ([gist summary of Manus](https://gist.github.com/cedrickchee/b9646b3007b4a15f528351abd331984f)). Claude Code is the worked reference: plan mode and skills append messages, file edits produce an appended `<system-reminder>` instead of rewriting earlier reads, CLAUDE.md edits apply only after `/clear`, `/compact` or restart, workflow fan-outs hold siblings up to 5 seconds so they read the first agent's cached prefix, and its list of cache-busters (switching model, changing effort except on 5.5-generation and Fable 5.1 models, connecting or removing an MCP server, denying a whole tool, compaction) is the checklist of operations to avoid mid-session or push into forks ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). Total input is `cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, and unexpected misses should be treated as regressions.

### A compaction ladder, cheapest and most reversible rung first

| Rung | Technique | Defaults and parameters | Reversible | Reference |
|---|---|---|---|---|
| 1 | Cap and paginate tool output at ingestion | 25,000-token cap; `response_format` concise/detailed; truncation notes that coach narrower queries | Yes | [Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents) |
| 2 | Offload large outputs to files, keep path plus preview | Drop content that already exists in the environment or filesystem | Yes | [Manus summary](https://gist.github.com/cedrickchee/b9646b3007b4a15f528351abd331984f); [deepagents middleware](https://github.com/langchain-ai/deepagents/tree/main/libs/deepagents/deepagents/middleware) |
| 3 | Clear stale tool results | `clear_tool_uses_20250919`: trigger 100,000 input tokens, `keep` last 3 tool uses, `clear_at_least`, `exclude_tools`, `clear_tool_inputs` | Partly (client keeps history) | [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing) |
| 4 | Clear old thinking | `clear_thinking_20251015`, `keep: {type:"thinking_turns", value:N}`, listed first | Partly | [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing) |
| 5 | Summarize older turns, keep recent tail verbatim | Anthropic `compact_20260112` (default 150,000, minimum 50,000) or on-demand `compact-2026-09-04`; OpenAI `/responses/compact` or `compact_threshold`; Codex min(configured, 90% of window); Claude Code ~967K on native-1M models | No | [Threshold](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold); [On demand](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand) |
| 6 | Re-inject durable state | Root CLAUDE.md/AGENTS.md, memory index, plan, git status, up to 5 recent files (≤5k tokens each), skill bodies (5k each, 25k total) | n/a | [Claude Code context window](https://code.claude.com/docs/en/context-window) |
| 7 | Fresh context from external state | `new_context` tool, or reset bootstrapped from progress and feature files | n/a | [Codex handlers](https://github.com/openai/codex/tree/main/codex-rs/core/src/tools/handlers) |

The API details decide whether compaction works. Anthropic threshold compaction adds `{"type":"compact_20260112"}` to `context_management.edits` under header `compact-2026-01-12`, with `trigger` defaulting to `{"type":"input_tokens","value":150000}`; `pause_after_compaction: true` stops with `stop_reason: "compaction"` so the client can re-insert content or count compactions to enforce a total budget, and `instructions` replaces the default prompt ([Threshold compaction](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold)). The summary comes from the request's own model (no cheaper summarizer), the model sometimes calls a tool instead of summarizing (fixed with "Do not call any tools while writing this summary; respond with text only"), thinking before the compaction block is not carried forward on Claude 5.1+, the true cost hides in `usage.iterations`, and a `cache_control` on the compaction block plus a separate breakpoint at the end of the system prompt keeps the system cache alive. Anthropic now recommends on-demand compaction "wherever it is available": send the conversation with `"compaction": {"type":"summarize"}` and the identical `system` and `tools`, allow several thousand `max_tokens`, optionally pass `instructions` of up to 16,384 characters, and place the single signed `compaction` block first in `messages`, unmodified, on every later request ([On-demand compaction](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand)). It cannot be combined with `context_management`, it drops images, documents and mid-conversation system instructions inside the summarized range, and it fails silently as HTTP 200 with empty content, so the harness must compact before overflow by projecting the next request from the last `usage`. Keep-tail compaction is client-side (the cut must not split a tool call from its result; the reference keeps the last two turns), and background compaction records the message count N at request time and swaps exactly the first N messages when the block arrives, removing the user-visible pause ([Keep recent turns](https://platform.claude.com/docs/en/build-with-claude/compaction-keep-recent-turns); [Background compaction](https://platform.claude.com/docs/en/build-with-claude/compaction-background)). OpenAI's `/responses/compact` is stateless and returns an encrypted compaction item that must not be pruned, while `context_management.compact_threshold` compacts server-side (examples use 200,000 with `store=false`) ([OpenAI compaction](https://developers.openai.com/api/docs/guides/compaction), via search); because that item is opaque, a cross-provider harness must keep its own readable task state.

Harness recipes differ mainly in thresholds. Codex's local recipe is the most portable: a "CONTEXT CHECKPOINT COMPACTION" prompt that asks for "a handoff summary for another LLM that will resume the task," re-injected behind the prefix "Another language model started to solve this problem…", plus the user's own prior messages newest-first up to `COMPACT_USER_MESSAGE_MAX_TOKENS = 20_000` and the re-inserted initial context ([compact.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs); [prompt.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/compact/prompt.md)); it fires at `min(model_auto_compact_token_limit, 90% of the window)` and reserves headroom with `effective_context_window_percent` defaulting to 95% ([openai_models.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/openai_models.rs)). Gemini CLI compresses at 50% of the window and keeps the latest 30% ([chatCompressionService.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/context/chatCompressionService.ts)); OpenHands summarizes the first half of events with `keep_first=2` and `max_size=240` ([condenser README](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/README.md)); Manus reportedly tracks a "pre-rot threshold" of roughly 128K–200K tokens and exhausts reversible compaction before irreversible summarization ([ZenML](https://www.zenml.io/llmops-database/context-engineering-for-production-ai-agents-at-scale), secondary). Claude Code compacts at ~967K on native-1M models, overridable with `CLAUDE_CODE_AUTO_COMPACT_WINDOW` or a per-subagent `autoCompactWindow` ([Model config](https://code.claude.com/docs/en/model-config)); that default optimizes continuity and cost, so precision-sensitive applications should set it lower (an inference, since no public quality-versus-threshold curve exists). The summary schema should merge the Anthropic SDK and Codex prompts (task and constraints, current state and files touched, decisions and rationale, errors and failed approaches, next steps, user preferences, plus an explicit "do not call tools"), and the deprecated SDK compactor's shrinkage of ~100k tokens to "~2–3k tokens" is a useful sizing target ([Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)).

Measured gains justify the ladder. In Anthropic's agentic-search eval, context editing alone improved performance **29%** and memory plus context editing **39%**, and in a 100-turn web-search eval context editing cut token use **84%** while letting otherwise-failing runs finish ([Claude blog](https://claude.com/blog/context-management)). Research is now learning these operations: ACON cuts peak tokens 26–54% on AppWorld, OfficeBench and multi-objective QA while largely preserving accuracy ([arXiv 2510.00615](https://arxiv.org/abs/2510.00615)); Context-Folding's RL-trained `branch`/`return` actions match baselines with up to 10× smaller active context ([arXiv 2510.11967](https://arxiv.org/abs/2510.11967)); and Recursive Language Models, which hold the prompt as a REPL variable and recurse on chunks, reportedly score 91.3 versus 70.5 for a compaction agent on 6–11M-token BrowseComp-Plus ([arXiv 2512.24601](https://arxiv.org/abs/2512.24601), secondary numbers).

Models also need to see their budget. One-million-token windows are the default on current Claude models (128k maximum output; overflow stops with `stop_reason: "model_context_window_exceeded"`), and Sonnet 5, Sonnet 4.6, Sonnet 4.5 and Haiku 4.5 automatically receive `<budget:token_budget>` plus per-tool-call `<system_warning>Token usage: 35000/200000; 165000 remaining</system_warning>` tags, while Opus 4.7+, Sonnet 5.5, Fable and Haiku 5.5 do not ([Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)). For those models, task budgets (beta `task-budgets-2026-03-13`, `output_config.task_budget = {type:"tokens", total}`, minimum 20,000) inject a server-side countdown over one agentic turn; they are advisory, survive compaction, and when set too small cause refusal-like early stopping ([Task budgets](https://platform.claude.com/docs/en/build-with-claude/task-budgets)). Elsewhere, inject a short turn-scoped "tokens used / remaining / next compaction at N" note. Finally, map guards to Drew Breunig's four failure modes ([Breunig](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html)): verify facts before they enter notes (poisoning), use quality-oriented compaction and subagent quarantine (distraction), use tool search and path-scoped instructions (confusion), and lint instruction files while keeping one source of truth for task state (clash). Keep failed actions and error traces in context so the model updates its beliefs, but compactly; vary serialization to avoid few-shot ruts; recite the plan near the end of context; and update persistent playbooks with ACE-style delta bullets rather than full rewrites to avoid "context collapse" ([ACE](https://github.com/ace-agent/ace)).

## Memory: a small loaded index, on-demand files, background consolidation

Memory design starts by separating two persistence layers that harnesses keep distinct. **Task state** (the JSON feature list, progress log, init script and git commits from the long-horizon section) belongs to one task and is re-read at every session start; **learned memory** (preferences, corrections, environment gotchas, workflows, skills) crosses tasks. Claude Code explicitly keeps derivable project state out of auto memory, skipping anything recoverable from code, git or CLAUDE.md ([Claude Code memory](https://code.claude.com/docs/en/memory)). Within learned memory, 2025–2026 surveys converge on a write → manage → read loop and on classifying memory by function (factual, experiential, working) rather than by "short versus long term" ([Hu et al. survey](https://arxiv.org/abs/2512.13564v1); [arXiv 2603.07670](https://arxiv.org/html/2603.07670v1)). The practical taxonomy that Claude Code, Codex, the Agents SDK and Letta Code all converged on has two axes: function (semantic facts and preferences, episodic rollout summaries, procedural skills and lessons, working scratch) and loading policy (always-loaded instructions and a small index, on-demand topic files and skills, and evidence-only raw transcripts).

Anthropic ships three layers. The API memory tool (`{"type": "memory_20250818", "name": "memory"}`, stable, ZDR-eligible) is client-side: Claude emits `view`, `create`, `str_replace`, `insert`, `delete` and `rename` calls against a `/memories` prefix that the application maps to any storage, `view` truncates past 16,000 characters, and the API auto-injects a protocol beginning "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE" and warning "ASSUME INTERRUPTION: Your context window might be reset at any moment" ([Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). The implementer owns security: canonicalize paths and reject `../`, `..\\` and `%2e%2e%2f`, cap file sizes and view output, and expire files not accessed in a long time; near the context-editing threshold Claude gets an automatic warning to save results before they are cleared ([Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)). Claude Code's auto memory lives in `~/.claude/projects/<project>/memory/` as a `MEMORY.md` index with "one line per memory" plus one topic file each, typed in frontmatter as `user`, `feedback`, `project` or `reference`; only the **first 200 lines or 25KB** of the index load at session start, the harness stamps a `modified` timestamp on writes, and near the limit it tells Claude to "keep one line per entry, move detail into topic files, and merge or drop stale entries" ([Claude Code memory](https://code.claude.com/docs/en/memory)). Subagents get their own memory via a `memory:` field (`user`, `project` or `local`). Managed Agents memory stores (beta header `agent-memory-2026-07-22`) mount workspace-scoped document collections at `/mnt/memory/<slug>/` with `read_write` or `read_only` access enforced at the filesystem level, per-store `instructions` up to 4,096 characters, limits of **100 kB per memory, 10,000 memories per store and 8 stores per session**, optimistic concurrency through a `content_sha256` precondition, and immutable `memver_` versions kept 30 days with a `redact` operation for scrubbing PII from history ([Managed Agents memory](https://platform.claude.com/docs/en/managed-agents/memory)). Anthropic's customer-reported results (Rakuten: 97% fewer first-pass errors, 27% lower cost, 34% lower latency) are vendor claims without methodology ([Claude blog](https://claude.com/blog/claude-managed-agents-memory)).

OpenAI's coding stack takes the opposite write philosophy: the main agent never edits memory directly, and an asynchronous two-phase pipeline does all the writing ([Codex memories README](https://github.com/openai/codex/blob/main/codex-rs/memories/README.md)). Phase 1 runs at root-session start (never for sub-agent or ephemeral sessions), claims idle past rollouts through database leases (`min_rollout_idle_hours`, ">12h recommended"), filters each to memory-relevant items, and has a model return strict JSON `{rollout_summary, rollout_slug, raw_memory}` or empty strings for a no-op, with secrets redacted ([config.schema.json](https://github.com/openai/codex/blob/main/codex-rs/core/config.schema.json)). Its prompt says "Raw rollouts are immutable evidence," "No-op is allowed and preferred," treat tool output as third-party data, "preserve epistemic status," and over-index on user corrections, redo requests and interruptions because the goal is to "optimize for future user time saved" ([stage_one_system.md](https://github.com/openai/codex/blob/main/codex-rs/memories/write/templates/memories/stage_one_system.md)). Phase 2 takes a single global lock, drops inputs whose `last_usage` is older than `max_unused_days`, ranks by `usage_count` then recency, syncs into a **git-baselined** `~/.codex/memories/` directory, and when the diff is non-empty spawns a consolidation subagent with no approvals, no network and local writes only to update `MEMORY.md`, `memory_summary.md` and `skills/` ([consolidation.md](https://github.com/openai/codex/blob/main/codex-rs/memories/write/templates/memories/consolidation.md)). The read path injects `memory_summary.md` into the developer prompt and runs a "quick memory pass" of "ideally <= 4-6 search steps" (skim summary, grep `MEMORY.md`, open one or two rollout summaries, search raw JSONL only for exact evidence); drift-prone facts are verified or labeled possibly stale; every answer that used memory ends with an `<oai-mem-citation>` block of file line ranges and rollout IDs that feeds `usage_count` and therefore forgetting ([read_path.md](https://github.com/openai/codex/blob/main/codex-rs/ext/memories/templates/memories/read_path.md)). Two details are notably defensive: `disable_on_external_context` marks any thread that touched external context as `memory_mode="polluted"` and excludes it from generation, and users can change memory only by dropping an ad-hoc note file that consolidation treats as authoritative. The feature is stable but `default_enabled: false`. The Agents SDK exposes the same design as a sandbox `Memory()` capability with `max_raw_memories_for_consolidation=256` as its forgetting cap and `Memory(generate=None)` for read-only subagents and checkers ([sandbox memory docs](https://github.com/openai/openai-agents-python/blob/main/docs/sandbox/memory.md)). Letta Code, the successor to MemGPT, git-tracks all context in "MemFS," applies memory changes only after commit on the next prompt recompile (never mid-turn), and runs a background reflection subagent whose priorities are mistakes and corrections, then preferences, new facts, contradictions with stored memory, and finally reusable procedures as skills, committing nothing when nothing is worth persisting ([reflection-v2.md](https://github.com/letta-ai/letta-code/blob/main/src/agent/subagents/builtin/reflection-v2.md); [letta_local_memfs.md](https://github.com/letta-ai/letta-code/blob/main/src/agent/prompts/letta_local_memfs.md)). DeepSeek has no verifiable first-party memory system; its MIT "DeepSeek Harness" relies on third-party plugins ([deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)).

The benchmark evidence favors simple file memory and append-only facts. A GPT-4o-mini agent given LoCoMo histories as files with grep and semantic `search_files` scored **74.0%**, above Mem0's best graph variant at 68.5% ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory), secondary), and in Mem0's own 2025 paper full context (72.90%) beat Mem0 (66.88%), though at 17.12 s versus 1.44 s p95 latency ([arXiv 2504.19413](https://arxiv.org/abs/2504.19413)). Mem0's April 2026 algorithm then abandoned LLM-decided UPDATE/DELETE for **single-pass ADD-only extraction** with entity linking, fused semantic + BM25 + entity retrieval and temporal ranking, reporting LoCoMo 91.6 and LongMemEval 93.4 in open source (92.5 and 94.4 on its platform) at roughly 7K retrieved tokens, with graph memory removed from OSS and `top_k` defaulting to 20 ([mem0](https://github.com/mem0ai/mem0); [v2→v3 migration](https://github.com/mem0ai/mem0/blob/main/docs/migration/oss-v2-to-v3.mdx)); Graphiti likewise invalidates old facts with validity windows rather than deleting them ([graphiti](https://github.com/getzep/graphiti)). These conversational-recall benchmarks are now near saturation and poorly predictive: MemoryArena found agents near ceiling on LoCoMo perform poorly on interdependent multi-session agentic tasks ([arXiv 2602.16313](https://arxiv.org/abs/2602.16313)), and LongMemEval-V2 (451 questions over histories up to 115M tokens) scores latency alongside accuracy across abilities such as workflow knowledge, environment gotchas and premise awareness ([LongMemEval-V2](https://github.com/xiaowu0162/LongMemEval-V2)). Procedural memory shows the sharpest split: on SkillsBench (84 tasks, 7,308 trajectories) **curated skills added 16.2 points on average while self-generated skills added nothing** (−1.3 in the NeurIPS version) ([arXiv 2602.12670](https://arxiv.org/html/2602.12670v1)), yet structured, verified experience works, with ReasoningBank adding 4.6–8.3 points on WebArena with ~16% fewer steps ([ICLR 2026](https://iclr.cc/virtual/2026/poster/10007887)), Agent Workflow Memory +51.1% relative on WebArena ([arXiv 2409.07429](https://arxiv.org/abs/2409.07429v1)) and ACE +10.6% on AppWorld through itemized delta updates ([ACE](https://github.com/ace-agent/ace)).

Memory is also an attack surface. Managed Agents' docs warn that with `read_write` access "a successful prompt injection could write malicious content into the store," which later sessions then read "as trusted memory" ([Managed Agents memory](https://platform.claude.com/docs/en/managed-agents/memory)), and MemoryGraft shows that implanted "successful experiences" can hijack experience-style memory ([arXiv 2512.16962](https://arxiv.org/pdf/2512.16962.pdf)); a January 2026 study notes "minimal empirical studies" of defense effectiveness ([arXiv 2601.05504](https://arxiv.org/abs/2601.05504v1)). The recommended design combines both labs' philosophies. Store memory as Markdown files with frontmatter recording type, scope, provenance and usage; keep a bounded index (≤200 lines or 25KB) always loaded; keep procedures in `skills/` and evidence in `rollout_summaries/`; version everything in git or a versioned object store; and add an optional BM25 + embedding + entity/time index behind the same file abstraction only when scale demands it. Write through two channels, an inline path-sandboxed and size-capped memory tool for explicit "remember X" requests plus a background Phase-1 extractor on idle, untainted sessions and a single-writer Phase-2 consolidator that makes delta edits with supersession notes rather than whole-file rewrites (ACE's "context collapse" is the argument against rewrites). Gate promotion of lessons into skills on verification evidence, mount shared organizational memory read-only, and evaluate memory on cross-session task outcomes, tokens and latency rather than on LoCoMo.

```yaml
---
type: feedback            # user | feedback | project | reference | lesson | workflow
scope: project            # org | user | project | agent
status: active            # active | superseded | stale
supersedes: null
provenance: {sessions: [s_8f2c], evidence: ["rollout_summaries/s_8f2c_fix-ci.md:12-30"], verified: true}
created: 2026-10-30T12:00:00Z
modified: 2026-11-02T09:14:00Z
last_used: 2026-11-03T08:00:00Z
use_count: 4
---

```

## Tools and protocols: a five-tool kernel, a searchable catalog, open standards

Every leading coding harness converged on a small kernel: a shell, file read and search, a structured edit primitive, a plan or todo tool, web search and fetch, subagent spawn and MCP passthrough. Claude Code's names (`Bash`, `Read`, `Edit`, `Write`, `Glob`, `Grep`, `WebFetch`, `WebSearch`, the `Agent` tool) double as permission-rule and hook-matcher keys ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference)); Codex registers `exec_command` plus `write_stdin` (PTY sessions keyed by `session_id`), `apply_patch`, `update_plan`, `view_image`, `web_search`, `tool_search`, `request_user_input`, `spawn_agent`/`wait_agent` and MCP resource tools ([Codex handlers](https://github.com/openai/codex/tree/main/codex-rs/core/src/tools/handlers)); and Pi gets by with four. Anthropic's stated rationale is "give your agents a computer" ([Claude blog](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)): bash plus files offers an unbounded action space through composition, context-economy primitives (grep, `head`, `tail`, `jq`), persistent state across turns, direct reuse of pretraining on shell transcripts, and a single choke-point where one OS sandbox covers every subprocess.

Tool design is now an empirical discipline. Anthropic's guidance is to build task-shaped tools rather than API wrappers (`schedule_event` instead of `list_users` + `list_events` + `create_event`; `search_logs` instead of `read_logs`), namespace by service and resource (`asana_search`, `jira_search`), return semantic fields (`name`, `file_type`) instead of UUIDs and MIME types, expose a `response_format` enum (a Slack example used 206 tokens detailed versus 72 concise), paginate and truncate with sensible defaults (Claude Code caps tool responses at **25,000 tokens**), and write specific, actionable errors that include a correct-input example ([Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). The ACI appendix adds poka-yoke arguments (requiring absolute paths eliminated a class of errors after `cd`) and formats close to natural internet text, avoiding diff hunk headers that require line counts or code wrapped in JSON that requires escaping ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). `input_examples` with 1–5 realistic calls raised complex-parameter accuracy from **72% to 90%** ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Schemas should be strict wherever supported: OpenAI's strict mode requires `additionalProperties: false` and every property in `required` with optional fields as nullable unions ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), via search), while DeepSeek's beta strict mode (`base_url="https://api.deepseek.com/beta"`) supports `pattern` and `minimum`/`maximum` but not `minLength`/`maxLength` or `minItems`/`maxItems` ([DeepSeek tool calls](https://api-docs.deepseek.com/guides/tool_calls/)), so the harness needs a per-provider schema compiler. Validation failures belong in tool results (`isError`) "to enable model self-correction," per MCP SEP-1303 ([MCP 2025-11-25 changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/changelog.mdx)). Descriptions should be iterated against evals: a tool-testing agent that rewrote a flawed MCP description cut later agents' task completion time by 40% ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).

The edit format is the main remaining divergence and should be selected per model. Codex's `apply_patch` envelope (`*** Begin Patch`, `*** Add File:`, `*** Update File:`, `*** Delete File:`, `*** Move to:`, `@@` context anchors, `+`/`-`/space lines, `*** End Patch`, no line numbers) is defined by an official Lark grammar and exposed as a FREEFORM grammar-constrained tool ("do not wrap the patch in JSON"), applied with a `seek_sequence` matcher that falls back from exact to trim-end to trim to Unicode-normalized matching, and parsed incrementally by a streaming parser ([parser.rs](https://github.com/openai/codex/blob/main/codex-rs/apply-patch/src/parser.rs); [seek_sequence.rs](https://github.com/openai/codex/blob/main/codex-rs/apply-patch/src/seek_sequence.rs); [apply_patch_spec.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/apply_patch_spec.rs)). OpenAI says "We strongly recommend using our exact apply_patch implementation as the model has been trained to excel at this diff format" ([Codex prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide), via search), and the envelope has spread to OpenCode, the Agents SDK sandbox, gpt-oss, OpenHands and Aider. The `old_string`/`new_string` replace family (Claude-style edit, Gemini CLI `edit`, Crush `edit`/`multiedit`, Pi `edit`) serves Claude-style models, and Aider's per-model edit-format table remains the best precedent for routing ([Aider edit formats](https://github.com/Aider-AI/aider/blob/main/aider/website/docs/more/edit-formats.md)). For the shell, a PTY session pair (`exec_command` + `write_stdin`) handles interactive processes and dev servers, while mini-swe-agent's stateless `subprocess.run` is simpler to sandbox and scale; the right default is PTY sessions with a stateless mode for evaluation and RL. Optional power tools worth copying are LSP operations as tools (Crush's `lsp_rename`, `lsp_definition`, diagnostics) ([Crush tools](https://github.com/charmbracelet/crush/tree/main/internal/agent/tools)) and Aider's tree-sitter repo map with a 1,024-token default budget ([repomap.py](https://github.com/Aider-AI/aider/blob/main/aider/repomap.py)).

Large catalogs must be deferred, searched and called from code. Five MCP servers with 58 tools cost about 55K tokens of definitions (Jira alone ~17K, with 134K observed before optimization), and Claude's tool-selection accuracy "degrades once you exceed 30–50 available tools" ([Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)). Marking tools `defer_loading: true` behind `tool_search_tool_regex_20251119` (Python regex up to 200 characters) or `tool_search_tool_bm25_20251119` (natural language up to 500 characters) loads 3–5 tools per request out of up to 10,000, cuts definition tokens **over 85%**, and lifted MCP-eval accuracy from 49% to 74% on Opus 4 and **79.5% to 88.1% on Opus 4.5**; keep the 3–5 most-used tools hot, never defer the search tool itself, and switch on deferral once definitions exceed 10K tokens or 10+ tools ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Claude Code now defers MCP tool definitions by default ([Claude Code costs](https://code.claude.com/docs/en/costs)), OpenAI's `tool_search` is reportedly gpt-5.4+ only, and `allowed_tools` restricts callable tools per turn without changing the cached `tools` list ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), via search). Programmatic tool calling lets Claude call tools marked `allowed_callers: ["code_execution_20260120"]` as async Python functions inside the code-execution container (the November 2025 launch used `code_execution_20250825`), so intermediate results never enter context: average tokens fell from 43,588 to 27,297 (**−37%**) and GAIA rose from 46.5% to 51.2%, though it is not ZDR-eligible and `allowed_callers` "is guidance, not a security boundary" ([PTC docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)). Presenting MCP servers as a filesystem code API (`servers/<server>/<tool>.ts`) took one workflow from **150,000 to 2,000 tokens** and enables PII tokenization between tools ([Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)); Codex's `code-mode` crates are the OpenAI analogue. Anthropic's recommended rollout order is to cache tool definitions from day one, add tool search past about 20 tools, then context editing for long runs, then programmatic calling for chains ([Manage tool context](https://platform.claude.com/docs/en/agents-and-tools/tool-use/manage-tool-context)).

MCP is the universal tool bus, and a new client should target the **2026-07-28** revision. It removes protocol sessions, `Mcp-Session-Id` and the `initialize` handshake; every request carries `io.modelcontextprotocol/protocolVersion` and `clientCapabilities` in `_meta`; servers must implement `server/discover`; Multi Round-Trip Requests replace server-initiated sampling, elicitation and roots with an `InputRequiredResult` (`resultType: "input_required"`) that the client answers by retrying with `inputResponses`; requests carry `Mcp-Method`/`Mcp-Name` headers; list results are `CacheableResult`s with `ttlMs` and `cacheScope`; servers SHOULD return `tools/list` in deterministic order "to improve LLM prompt cache hit rates"; long-running work uses the `io.modelcontextprotocol/tasks` extension (`tasks/get`, `tasks/update`); `_meta` carries OpenTelemetry `traceparent`; and Roots, Sampling, Logging, the HTTP+SSE transport and Dynamic Client Registration are deprecated in favor of CIMD with RFC 9207 `iss` validation, under a ≥12-month deprecation policy ([MCP 2026-07-28 changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx)). Adoption is no longer in question: "close to half-a-billion downloads a month" across Tier 1 SDKs at GA ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)), under the Linux Foundation's Agentic AI Foundation since December 9, 2025 ([MCP AAIF post](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2025-12-09-mcp-joins-agentic-ai-foundation.md)). The client checklist is stateless requests with a fallback to `initialize` for older servers, `input_required` surfaced to the user then retried, `tools/list` cached by `ttlMs` with deterministic ordering, CIMD-first OAuth with RFC 8707 resource indicators, and no new features built on Sampling or Roots. Treat `ToolAnnotations` (`readOnlyHint` default false, `destructiveHint` default true, `idempotentHint` default false, `openWorldHint` default true) as untrusted hints unless the server is vetted; the maintainers note that no client yet filters by them ([MCP annotations post](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2026-03-16-tool-annotations.md)).

Instructions and procedures have their own standards. Agent Skills (open standard since December 18, 2025, spec at agentskills.io) package a procedure as a folder with `SKILL.md` whose YAML frontmatter holds `name` (≤64 characters) and a `description` stating what it does and when to use it, loaded by three-level progressive disclosure: ~100 tokens of metadata always present, a body under 5k tokens (and under 500 lines) on trigger, and bundled scripts and references at zero cost until used, with only script output entering context ([Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview); [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). Codex, the Agents SDK (`Skills(lazy_from=…)`), Gemini CLI, deepagents, Letta Code, Pi, OpenHands and Crush all load SKILL.md folders ([anthropics/skills](https://github.com/anthropics/skills/blob/main/README.md)); skills can exfiltrate, so audit third-party ones ([Anthropic](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)), and put critical instructions at the top because Claude Code re-injects skill bodies after compaction truncated from the end at 5k tokens each ([Claude Code context window](https://code.claude.com/docs/en/context-window)). AGENTS.md, donated by OpenAI to the AAIF, is the cross-vendor "README for agents" ([agents.md](https://github.com/agentsmd/agents.md)). Codex collects every AGENTS.md from project root to the working directory, honors `AGENTS.override.md`, enforces a `project_doc_max_bytes` budget, and lets more deeply nested files and direct instructions take precedence ([agents_md.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/agents_md.rs); [Codex prompt.md](https://github.com/openai/codex/blob/main/codex-rs/models-manager/prompt.md)); Claude Code reads AGENTS.md when no CLAUDE.md exists, recommends **under 200 lines per file** because "longer files consume more context and reduce adherence," loads subdirectory files and `.claude/rules/*.md` with `paths:` globs lazily, follows `@path` imports up to four hops, strips HTML comments, and offers `/doctor prompt-audit` for contradictions ([Claude Code memory](https://code.claude.com/docs/en/memory)). The layering principle is simple: instruction files hold always-true facts, skills hold procedures, tools hold actions, and hooks enforce, because instructions are context, not enforcement. For agent-to-agent traffic across organizational boundaries, A2A v1.0 (Agent Cards at `/.well-known/agent-card.json`, signed cards, JSON-RPC, gRPC and REST bindings) is the standard, but inside one harness files, function calls and git remain simpler ([A2A spec](https://a2a-protocol.org/latest/specification/), via search).

## Execution: sandbox the whole process tree and proxy every outbound byte

Because bash is the universal tool, the security story is "sandbox the shell" rather than "secure each tool," and both isolation layers are mandatory. Claude Code's sandbox confines reads and writes to the working directory and routes all network traffic through a Unix-socket proxy outside the sandbox that enforces a domain allowlist; Anthropic stresses that "both layers are required," since without network isolation a compromised agent can exfiltrate SSH keys and without filesystem isolation it can escape to gain network access ([Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)). The UX payoff is as important as the security: sandboxing "safely reduces permission prompts by **84%**" in Anthropic's internal usage, because in-boundary actions no longer need approval, and the threat model is explicit that "a successful prompt injection is fully isolated."

Two open implementations are directly reusable. Anthropic's Apache-2.0 `sandbox-runtime` (`srt`, beta research preview) wraps arbitrary processes, including local MCP servers via `"command": "srt"`, without a container: Seatbelt profiles generated per policy on macOS, bubblewrap with the network namespace removed on Linux (traffic flows to host HTTP and SOCKS5 proxies over bind-mounted Unix sockets, requiring `bwrap` and `socat`), and an alpha Windows mode using a dedicated user, write-restricted token and WFP egress filter ([sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)). Its policy semantics are the ones to copy: reads allowed by default with deny-then-allow (a more specific `denyRead` such as `**/.env` stays denied), writes denied by default and allow-only with `denyWrite` precedence, network denied by default with `allowedDomains`/`deniedDomains`, violations surfaced to the model in a `<sandbox_violations>` block so it can adapt, and live policy updates over `--control-fd`. Codex's sandbox offers four `SandboxPolicy` variants (`read-only`, `workspace-write` with `writable_roots`, `external-sandbox` for when the harness already runs in a container or VM, and `danger-full-access`), keeps `.git` (notably `.git/hooks`) and `.codex` read-only even inside writable roots to block privilege escalation, uses bubblewrap plus seccomp with `PR_SET_NO_NEW_PRIVS` as the Linux default (Landlock is legacy; WSL1 is rejected), and ships Seatbelt profiles and Windows sandbox crates ([protocol.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs); [linux-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)). Its network proxy listens on `127.0.0.1:3128` (HTTP) and `127.0.0.1:8081` (SOCKS5), supports a `mode = "limited"` read-only network with HTTPS interception through a managed CA, and blocks private and LAN destinations even when an allowlisted hostname resolves to one ([network-proxy README](https://github.com/openai/codex/blob/main/codex-rs/network-proxy/README.md)); `--dangerously-bypass-approvals-and-sandbox` is documented as "EXTREMELY DANGEROUS" and only for externally sandboxed environments ([shared_options.rs](https://github.com/openai/codex/blob/main/codex-rs/utils/cli/src/shared_options.rs)).

| Deployment | Isolation | Network | Secrets | Reference |
|---|---|---|---|---|
| Local CLI or IDE | OS sandbox around every subprocess and local MCP server: Seatbelt (macOS), bubblewrap + seccomp (Linux), restricted token + WFP (Windows) | Namespace removed; host HTTP/SOCKS5 proxy with domain allowlist and private-IP blocking | Read-deny `~/.ssh`, `.env`; keep `.git/hooks` and harness config read-only | `srt`; Codex sandboxing and network-proxy crates |
| Cloud session | Per-session microVM (Firecracker) or user-space kernel (gVisor), provisioned lazily | Egress proxy with allowlist | Never inside the sandbox; a proxy injects credentials and validates operations (e.g., push only to the session branch) | [Claude Code on the web](https://www.anthropic.com/engineering/claude-code-sandboxing); Managed Agents |
| Eval and RL | One sandbox per rollout from a pre-warmed pool, or recycled between same-image runs | Per-task policy | None | [HF blog](https://huggingface.co/blog/sergiopaniego/rl-environments-2026); Harbor |
| Already containerized | `external-sandbox` mode to avoid double sandboxing | Container policy | Container policy | Codex `SandboxPolicy` |

Cloud agents use per-session VMs or containers with credentials held outside. Claude Code on the web never places git credentials or signing keys inside the sandbox; a custom git proxy authenticates the sandbox's scoped credential, verifies the operation, then attaches the real token ([Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)). Vendor guidance favors Firecracker microVMs (E2B, ~150 ms cold starts) for untrusted code and gVisor (Modal) for lighter or GPU workloads, though cold-start figures across vendors conflict and no independent escape-resistance benchmark exists ([Northflank](https://northflank.com/blog/daytona-vs-e2b-ai-code-execution-sandboxes), vendor-adjacent). OpenAI's SDK formalizes the environment as a `SandboxAgent` with a `Manifest` of workspace entries (`GitRepo`, `LocalDir`), capabilities (shell, filesystem, skills, memory, compaction), snapshots and clients for Docker, E2B, Modal, Daytona, Cloudflare, Vercel and Blaxel, and warns that the Unix-local client "adds no OS-level confinement" on Linux ([sandbox_agents.md](https://github.com/openai/openai-agents-python/blob/main/docs/sandbox_agents.md)); OpenAI's hosted shell runs in managed containers with no TTY and no sudo ([OpenAI shell guide](https://developers.openai.com/api/docs/guides/tools-shell), via search).

Recovery and parallelism need their own primitives. Claude Code snapshots files before edits ("press Esc twice to rewind"), but checkpoints are "separate from git," cannot undo remote side effects, and the SDK's file checkpointing tracks only `Write`, `Edit` and `NotebookEdit`, not Bash side effects ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works); [file checkpointing](https://code.claude.com/docs/en/agent-sdk/file-checkpointing)), so a robust harness adds git-level snapshots (a commit, stash or worktree per step) that capture shell changes too. Parallel writers each get a git worktree (Claude Code's `isolation: worktree`, Codex's `worktree` crate) or their own container. Tool output inside the sandbox should be engineered for context economy, as the 16-agent compiler project learned: print a few summary lines, send details to log files, tag failures with a grep-able `ERROR`, and offer a deterministic `--fast` sampling mode because agents are blind to wall-clock time ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)).

## Permissions and injection: auto-allow inside the boundary, classify every crossing

Manual approval does not scale: Anthropic found users "accept 93% of them anyway," a sign of approval fatigue rather than oversight ([Anthropic](https://www.anthropic.com/engineering/claude-code-auto-mode)). Harnesses have therefore converged on layered decision pipelines in which static rules, modes, hooks and a model reviewer resolve almost everything before a human is asked. The Claude Agent SDK's `permission_mode` values define the vocabulary: `default` (a `canUseTool` callback decides, and no callback means deny), `acceptEdits`, `plan` (no source edits), `dontAsk` (never prompts and denies anything not pre-approved, for headless use), `auto` (a model classifier reviews actions) and `bypassPermissions` (isolated environments only; TypeScript also requires `allowDangerouslySkipPermissions: true`, and it refuses to run as root), with rules scoped as in `"Bash(npm *)"` ([agent loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)). Auto mode is now the built-in starting mode for interactive Claude Code sessions ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). Codex's `AskForApproval` offers `untrusted` (approval unless an exec-policy rule allows), `on-request` (the default; the model decides when to ask), `granular` (per-category booleans where false auto-rejects rather than prompting) and `never` (failures return to the model), paired with per-mode prompt templates for `read_only`, `workspace_write` and `danger_full_access` ([protocol.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs); [permission templates](https://github.com/openai/codex/tree/main/codex-rs/prompts/templates/permissions)), and Gemini CLI ships named TOML policy profiles such as `read-only`, `plan`, `yolo`, `sandbox-default` and `non-interactive` ([Gemini policies](https://github.com/google-gemini/gemini-cli/tree/main/packages/core/src/policy/policies)).

Claude Code's auto mode (March 25, 2026) is the best-documented reviewer design. An input layer runs a server-side prompt-injection probe over tool outputs and annotates suspicious content; an output layer runs a two-stage transcript classifier on Sonnet 4.6 before each action, first a single-token yes/no filter told to "err on the side of blocking," then chain-of-thought re-evaluation only for flagged actions ([Anthropic](https://www.anthropic.com/engineering/claude-code-auto-mode)). The classifier is **reasoning-blind by design**: it sees user messages and tool calls but not assistant text or tool results, so injected text cannot argue with the reviewer, at the cost of weaker provenance. Actions flow through three tiers: a fixed allowlist of non-state-modifying tools plus user rules (entering auto mode drops blanket shell, wildcard interpreter and package-manager rules), in-project file edits that skip the classifier, and everything else (shell, web fetch, external tools, subagent spawns, out-of-project filesystem) sent to the classifier. A block returns as a tool result telling the agent to find a safer path rather than route around it; **3 consecutive or 20 total denials escalate to the human**, and headless `claude -p` terminates. Configuration has an environment slot (the trust boundary, by default the current git repo), more than 20 default block rules in four groups (destroy or exfiltrate, degrade security posture, cross trust boundaries, bypass review or affect others), and allow exceptions. The honest numbers matter:

| Dataset | Stage 1 only | Full pipeline |
|---|---|---|
| Real internal traffic (n=10,000), false-positive rate | 8.5% | **0.4%** |
| Real overeager actions (n=52), false-negative rate | 6.6% | **17%** ("the honest number") |
| Synthetic exfiltration (n=1,000), false-negative rate | 1.8% | 5.7% |

Most misses were cases where the classifier saw the danger but misjudged whether the user's consent covered the blast radius, which is why Anthropic says auto mode "reduces risk compared to --dangerously-skip-permissions but doesn't eliminate it" ([Claude blog](https://claude.com/blog/auto-mode)). Codex's equivalents are a guardian `auto_review` reviewer subagent selectable through `approvals_reviewer` ([guardian](https://github.com/openai/codex/tree/main/codex-rs/core/src/guardian)) and a Starlark exec policy: `prefix_rule(pattern=[...], decision="allow"|"prompt"|"forbidden", justification=..., match=[...], not_match=[...])` whose examples are validated as unit tests at load time, plus `host_executable(name="git", paths=[...])` to pin which absolute binaries may match a basename rule, checkable with `codex execpolicy check` ([execpolicy README](https://github.com/openai/codex/blob/main/codex-rs/execpolicy/README.md)). Hooks provide the remaining programmable layer (`PreToolUse` deny, ask or rewrite; `PermissionRequest`; `PermissionDenied` for auto-mode denials), and Anthropic's docs are blunt that CLAUDE.md instructions "are context, not enforcement" ([Claude Code memory](https://code.claude.com/docs/en/memory)).

Prompt injection remains unsolved at the model level, which is why the pipeline exists. Simon Willison's "lethal trifecta" (access to private data, exposure to untrusted content, and the ability to communicate externally) names the condition under which any agent can be tricked into leaking data, and he notes that guardrails catching "95% of attacks" are "a failing grade" in security ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/), via search). Vendor numbers show large but non-zero reductions that depend heavily on attacker strength. Against an adaptive best-of-N attacker in November 2025, Anthropic measured browser-use attack success of 8.0% for Opus 4.5 with the model alone and **1.4% with improved safeguards** (Sonnet 4.5: 13.8% to 1.9%), adding that "a 1% attack success rate… still represents meaningful risk" ([Anthropic](https://www.anthropic.com/research/prompt-injection-defenses)). Under a stronger August 2026 red-team eval for Claude in Chrome's general availability, Opus 4.5 reached 17.6% before safeguards while Opus 5 was at 3.8%, and Sonnet 5, Opus 5 and Mythos 5 with probes plus a safety classifier reached **0%** (Fable 5: 0.3%), using probes on tool results, an action classifier comparing each action to the original request, and admin domain allowlists ([Claude in Chrome GA](https://claude.com/resources/articles/claude-in-chrome-generally-available)). OpenAI hardens Atlas with an RL-trained attacker that finds long-horizon injections and feeds a rapid adversarial-training loop, and calls injection an open challenge for years to come ([OpenAI](https://openai.com/index/hardening-atlas-against-prompt-injection), via search). The two Anthropic evals use different attackers, so the 1.4% and 17.6% figures for the same model are not contradictory; they show that attacker strength dominates reported rates.

Architectural defenses therefore carry the load. The design-patterns paper by Beurer-Kellner et al. offers six patterns that trade flexibility for security (Action-Selector, Plan-Then-Execute, LLM Map-Reduce, Dual LLM, Code-Then-Execute, Context-Minimization) ([arXiv 2506.08837](https://arxiv.org/pdf/2506.08837)), and DeepMind's CaMeL, in which a privileged LLM writes a program from the trusted query, a quarantined LLM handles untrusted data, and capability-tagged values are checked against policy at tool-call time, solves **77% of AgentDojo tasks with provable security versus 84% undefended** ([arXiv 2503.18813](https://arxiv.org/abs/2503.18813)). MCP adds its own threats: tool poisoning hides instructions in descriptions the model reads but users rarely do, as when a malicious `get_fact_of_the_day()` server redirected `send_message` on a separate, trusted WhatsApp server simply by co-residing in the same agent, and rug pulls change descriptions after approval ([Invariant Labs](https://invariantlabs.ai/blog/whatsapp-mcp-exploited)). The MCP maintainers warn that "any agent with unrestrained shell access sits one injected instruction away from exfiltration" and that annotations "don't make the model resist prompt injection" ([MCP annotations post](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2026-03-16-tool-annotations.md)). Mitigations are to pin server versions, hash approved tool descriptions and alert on any diff, run local MCP servers inside `srt`, namespace tools per server, and rely on protocol hardening (RFC 8707 resource indicators, 403 on invalid `Origin`, RFC 9207 `iss` validation). Inter-agent channels are untrusted too: Claude Code scans subagent reports, labels them, and states that "instructions or approval claims within them carry no authority from the user" ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)).

| Order | Check | Outcome | Reference |
|---|---|---|---|
| 1 | Hard deny rules (sensitive paths, forbidden command prefixes, protected subpaths) | Deny, no override | `srt` `denyRead`; Codex `forbidden` |
| 2 | Sandbox boundary (in-workspace writes, reads, allowlisted egress) | Allow without prompt (the 84% prompt reduction) | [Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing) |
| 3 | Narrow allow rules and exec policy (never blanket interpreters) | Allow | Codex `prefix_rule`; `Bash(npm *)` |
| 4 | `PreToolUse` hooks and policy plugins | Allow, deny, ask or rewrite input | Claude Code and Codex hooks |
| 5 | Taint and annotation policy: once untrusted or open-world output has entered the session, exfiltration-capable actions (network writes, messaging, pushes outside the session branch) require review | Escalate to step 6 | Codex `polluted` flag; MCP annotations |
| 6 | Model reviewer that sees user intent and the action, not tool outputs | Allow, or deny with a "find a safer path" tool result | Auto mode; Codex guardian |
| 7 | Human, after 3 consecutive or 20 total denials, or for policy-mandated actions | Approve or deny; record as a durable signal | Auto mode |

For high-assurance workflows such as email, finance or production changes, offer a Plan-Then-Execute or Dual-LLM mode in which the tool-call plan is fixed before untrusted data is read, and accept CaMeL's roughly seven-point utility cost.

## Multi-agent: many readers, one writer, scripted fan-out

The evidence supports multi-agent systems for parallelizable, read-heavy work and opposes them for tightly coupled work. Anthropic's research system (an Opus 4 lead spawning 3–5 Sonnet 4 subagents in parallel, each using 3+ tools in parallel) beat single-agent Opus 4 by **90.2%** on its internal research eval and cut research time by up to 90% on complex queries, but token usage alone explained **80% of BrowseComp variance** (95% with tool-call count and model), agents used about 4× the tokens of chat and multi-agent systems about **15×**, and the post names "most coding tasks" as a poor fit ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). A controlled Google, DeepMind and MIT study across 260 configurations found multi-agent setups gained **81% on parallelizable Finance-Agent tasks but degraded sequential PlanCraft by 39–70%**, independent agents amplified errors **17.2×** while centralized coordination contained them best, returns turned negative once the single-agent baseline exceeded about 45%, and a predictive model picked the best architecture for 87% of unseen configurations ([arXiv 2512.08296](https://arxiv.org/pdf/2512.08296), via search snippet). Compiling a multi-agent system into one agent with a skill library matched its accuracy with 54% fewer tokens and 50% lower latency until selection degraded beyond roughly 50–100 skills ([arXiv 2601.04748](https://arxiv.org/pdf/2601.04748)), and at equal thinking-token budgets single agents match or beat multi-agent systems on multi-hop reasoning ([arXiv 2604.02460](https://www.alphaxiv.org/abs/2604.02460v1)). Homogeneous debate costs 2.1–3.4× the tokens of isolated self-correction for equal or lower accuracy ([arXiv 2605.00914](https://arxiv.org/pdf/2605.00914)). Cognition's April 2026 update captures the synthesis: most working multi-agent systems are "readonly" subagents that "mostly resemble tool calls," while Devin Review, which shares no prior context with the coding agent, catches about two bugs per Devin-written PR, roughly 58% of them severe, because "having a clean context makes the agent smarter" ([Cognition](https://cognition.com/blog/multi-agents-working), via search snippet). The decision rule is to fan out only when subtasks have low mutual dependency, outputs can be checked or merged without re-deriving each other's context, the single-agent baseline is weak or context-degraded, and the task justifies a 4–20× token multiple, and otherwise to prefer one agent plus a fresh-context reviewer.

Claude Code exposes four tiers with concrete limits. Subagents (the `Agent` tool, formerly `Task`) get their own context window, system prompt, tool allowlist and permissions, and return only a final report; nesting defaults to **3 levels** (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`) and concurrency to **20** (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), subagents launched from the main conversation run in the background by default and return `status: "async_launched"`, and they can be resumed by ID through `SendMessage` ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents); [Agent SDK subagents](https://code.claude.com/docs/en/agent-sdk/subagents)). Definitions take `description`, `prompt`, `tools`, `disallowedTools`, `model`, `effort`, `maxTurns`, `memory`, `skills`, `mcpServers`, `permissionMode`, `autoCompactWindow`, `background`, `omitClaudeMd` and `isolation: worktree`; a fresh subagent inherits only its task prompt, CLAUDE.md, a git status snapshot and preloaded skills, while a **fork** inherits the full parent conversation and tool pool, which answers Cognition's shared-context objection when it applies. The SDK docs add two operational warnings: "The only content you pass from parent to subagent is the Agent tool's prompt string," and "Claude Opus 5 delegates to subagents more readily than earlier models," so the `claude_code` preset adds a line telling it not to call the Agent tool unless asked and hard caps should be set regardless. Experimental agent teams add peers with a shared task list (file-locked claiming, dependencies, auto-unblocking), JSON mailboxes, and `TeammateIdle`/`TaskCreated`/`TaskCompleted` hooks where exit code 2 blocks completion; guidance is 3–5 teammates with 5–6 tasks each and a separate file set per teammate, because "two teammates editing the same file leads to overwrites" ([Agent teams](https://code.claude.com/docs/en/agent-teams)).

For large fan-outs, code-driven orchestration has displaced LLM-driven orchestration. Claude Code's dynamic workflows have Claude write a JavaScript script that a background runtime executes, so "Claude's context holds only the final answer" ([Workflows](https://code.claude.com/docs/en/workflows)). The script API is `agent(prompt, {schema, label, stallMs, model})`, `parallel()`, `pipeline(items, fn)`, `phase()` and `log()`; a `schema` forces JSON validated with up to 5 retries; concurrency defaults to **16** (`CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS`, 1–256) with limits of 4,096 items per `parallel` or `pipeline` and **1,000 agents per run**. Determinism makes runs resumable: `Date.now()`, `Math.random()` and `new Date()` throw, completed agents return cached results on relaunch until the first agent whose prompt differs, stalled agents restart up to 5 times, and a failure inside `parallel` yields `null` without ending the run. Cost guards warn above 25 agents or 1.5M projected tokens, size guidance runs small (<5), medium (<10, default) and large (<50), and siblings with identical model, effort, tools, schema and working directory share a prompt-cache prefix because the runtime holds them until the first response begins (`CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`, default 5,000). Built-in quality patterns include adversarial cross-review before reporting, "keep fixing until the type check passes or two rounds in a row make no progress," and claim-level voting in `/deep-research`, where uncheckable claims are labeled unverified rather than refuted. The OpenAI Agents SDK draws the same line, recommending orchestration "via code" because it is "more deterministic and predictable, in terms of speed, cost and performance," and offering two LLM-level primitives: handoffs (exposed to the model as `transfer_to_{agent_name}` tools, used when the specialist should own the answer) and `Agent.as_tool()` (used when a manager should own it) ([OpenAI multi_agent.md](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/multi_agent.md); [handoffs](https://github.com/openai/openai-agents-python/blob/main/src/agents/handoffs/__init__.py)). Codex's model-facing equivalents are `spawn_agent`, `send_input`, `wait_agent`, `close_agent`, `resume_agent` and `list_agents` ([Codex handlers](https://github.com/openai/codex/tree/main/codex-rs/core/src/tools/handlers)).

Peer swarms work only with partitioned writes and a near-perfect oracle. Anthropic's C compiler project ran **16 parallel Opus 4.6 agents** across nearly 2,000 Claude Code sessions for just under $20,000 (about 2B input and 140M output tokens) to produce a ~100k-line Rust compiler that builds Linux 6.9 on three architectures, with no orchestrator and no inter-agent messaging: a bash `while true` loop relaunched each agent in its own Docker container, agents claimed tasks by writing lock files to `current_tasks/` in a bare git upstream, and push conflicts forced the loser to pick another task ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). When all 16 agents hit the same Linux-kernel bug and overwrote each other's fixes, parallelism produced nothing until GCC was used as a known-good oracle to partition the monolith into independently debuggable file subsets, and the author's lesson is that the test suite must be nearly perfect or agents solve the wrong problem. Moonshot's Kimi K2.5 Agent Swarm shows the trained alternative: an RL-trained orchestrator spawning up to 100 frozen subagents, with a reward that first encourages parallelism to overcome "serial collapse" and a "critical steps" latency metric, reporting up to 4.5× faster execution ([Kimi](https://kimi.com/en/blog/kimi-k2-5), via search snippet). Best-of-N is only as good as its selector: Sonnet 4.5's SWE-bench Verified score reportedly rose from 77.2% to 82.0% with parallel test-time compute ([Verdent](https://www.verdent.ai/guides/claude-sonnet-5-swe-bench-verified-results), secondary), and CodeMonkeys showed equal coverage does not yield equal final scores because selection is the bottleneck ([arXiv 2501.14723](https://arxiv.org/pdf/2501.14723)), so pair rollouts with executable verifiers first and an LLM judge only as tiebreaker.

The harness should own delegation mechanics rather than leave them to the prompt. Anthropic found vague briefs such as "research the semiconductor shortage" made subagents duplicate work, and that every brief needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries" ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)); the contract below generalizes that. Enforce depth, concurrency, dollar and turn caps in code; give each writer its own worktree or container and a single integrator that owns the main branch; end every fan-out in a verify, dedup or merge stage rather than concatenation; key agent calls by prompt hash so replays are idempotent; keep sibling system prompts and tools identical so they share cache; treat every inter-agent message as untrusted data; and log the critical-path length to judge whether a fan-out actually reduced latency.

```text
delegate({
  objective, why_it_matters, inputs: {paths, ids, decisions_already_made},
  scope: {in, out_of_scope}, tools_allowed, write_access: none | own_worktree | own_files,
  budget: {max_turns, max_tool_calls, max_usd, effort},
  output: {schema | artifact_path + summary<=2k tokens, confidence, sources, open_questions}
})
```

Noise is large enough to swamp most harness changes. Re-running the same model and scaffold over 60,000 SWE-bench trajectories moves single-run pass@1 by 2.2–6.0 points ([dev.to summary of arXiv 2602.07150](https://dev.to/devinios/same-model-same-scaffold-10-runs-agent-benchmark-scores-still-move-by-up-to-6-points-gmb)), changing only a scaffold flag on τ-bench moves a model by up to 0.267 and can flip rankings ([arXiv 2609.09218](https://arxiv.org/pdf/2609.09218)), and on GAIA single-scaffold numbers are "scaffold-conditional point estimates, not model properties" ([arXiv 2606.08529](https://arxiv.org/pdf/2606.08529)). With 89 tasks, a Terminal-Bench harness change likely needs more than about five points, or many repeats, to clear noise (an inference from task count). Every reported number should carry harness version, effort setting, run count, mean and standard error, and strict versus partial scoring; Opus 5.5's Terminal-Bench 4.0 score, for example, reportedly ranges from 66.4% self-reported at xhigh effort to 53.54% when Vals.ai counts fallback-assisted tasks as failures ([Vals.ai](https://www.vals.ai/models/anthropic_claude-opus-5-5); [Vellum](https://www.vellum.ai/blog/claude-opus-5-5-benchmarks-explained), secondary).

Internal evals follow a methodology that Anthropic, OpenAI and Sierra share. Anthropic's January 2026 guide defines tasks, trials, graders, transcripts and outcomes, and states that "when we evaluate 'an agent,' we're evaluating the harness *and* the model working together" ([Anthropic](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)). Its roadmap is to start with "20-50 simple tasks drawn from real failures," write unambiguous tasks with a reference solution that two experts would agree on (since "0% pass@100 is most often a signal of a broken task"), balance positive and negative cases, isolate every trial in a clean environment (Claude once read git history left by previous trials), grade outcomes rather than paths with partial credit, give LLM judges an "Unknown" option, use one isolated judge per dimension, and read transcripts so that "failures should seem fair." Capability suites start at a low pass rate and graduate tasks into regression suites that sit near 100%. Report **pass@k** (at least one success in k) for exploratory tools and **pass^k** (all k succeed, p^k) for customer-facing agents, where 0.75 per-trial success becomes about 42% at k=3 and GPT-4o's retail agent fell to roughly 25% at pass^8 ([Sierra](https://sierra.ai/uk/blog/benchmarking-ai-agents)). Grader quality can dominate: Opus 4.5 scored 42% on CORE-Bench until grader bugs (such as rejecting "96.12" against "96.124991…") were fixed, then 95% with a less constrained scaffold. For research agents, a single LLM call returning 0.0–1.0 scores plus pass/fail across factual accuracy, citation accuracy, completeness, source quality and tool efficiency tracked human judgment best ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)); for tools, collect accuracy, runtime, call counts, tokens and tool errors on held-out tasks ([Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)); and OpenAI recommends trace grading while debugging, moving to dataset graders once behavior stabilizes ([OpenAI agent evals](https://developers.openai.com/api/docs/guides/agent-evals), via search). The resulting stack has five tiers: per-tool unit evals, a ~50-task capability suite in Harbor format with isolated containers, a regression suite on every PR and model bump, periodic public suites (Terminal-Bench via Harbor, SWE-bench Pro, τ² airline and retail with pass^k), and online trace grading on sampled production traffic, with turns, tool calls, tokens, cost and wall-clock reported as first-class outputs.

Observability should be instrumented against the OpenTelemetry GenAI semantic conventions so traces stay portable across Langfuse, Phoenix, Braintrust and LangSmith. The conventions define an `invoke_agent {gen_ai.agent.name}` span with `chat` children per model call and `execute_tool` children per tool call, though they remain in Development status and reportedly moved to a dedicated repository in mid-2026 ([OTel GenAI agent spans](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-agent-spans), via search; [Greptime](https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)), and MCP 2026-07-28 now propagates `traceparent` in `_meta`. Claude Code exports OTel metrics and events when `CLAUDE_CODE_ENABLE_TELEMETRY=1` (`OTEL_METRICS_EXPORTER`, `OTEL_LOGS_EXPORTER`, `OTEL_EXPORTER_OTLP_ENDPOINT`), including `claude_code.cost.usage` and `claude_code.token.usage` labeled by `token.type` (input, output, cacheRead, cacheCreation), on a 60,000 ms default interval ([Claude Code monitoring](https://code.claude.com/docs/en/monitoring-usage?m=1)), and the OpenAI Agents SDK traces model calls, tools, handoffs and guardrails by default ([OpenAI observability](https://developers.openai.com/api/docs/guides/agents/integrations-observability), via search). Among platforms, Langfuse (acquired by ClickHouse in January 2026, still MIT and self-hostable), LangSmith (online evals and failure clustering), Braintrust (eval-first CI gates) and Arize Phoenix (OTel-native, ELv2) cover most needs ([MarkTechPost](https://www.marktechpost.com/2026/08/09/top-llm-observability-and-evaluation-platforms-in-2026-langfuse-langsmith-braintrust-arize-and-more-compared/)). A minimal schema puts session ID, harness version, model, effort and the git SHA of prompts and tools on the root span; input, output, cache-read and cache-write tokens, time to first token, stop reason, retries and cost on each `chat` span; tool name, arguments hash, result tokens, truncation flag, error class, duration, idempotency key and sandbox ID on each `execute_tool` span; and custom spans for compaction, subagent spawn and approval waits. Dashboards should track cache-hit share, cost per successful task, tool error rate by tool, turns per task, p50 and p95 wall-clock, compaction frequency, denial rates and critical-path length. Message content should be opt-in or redacted: Anthropic's production research agent monitored "agent decision patterns and interaction structures" without reading conversation contents ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).

## Operations: durable steps, idempotent side effects, rainbow deploys

Long-running agents fail in ways chat systems do not, because "minor failures" compound across stateful runs; Anthropic's research system responded by building systems that "resume from where the agent was when the errors occurred," with regular checkpoints, retry logic, and agents explicitly told when a tool is failing so they can adapt ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). The production pattern is durable execution. Temporal's OpenAI Agents SDK integration reached general availability on March 23, 2026: agents run inside a Temporal Workflow, every model invocation runs as an Activity whose result is persisted, `OpenAIAgentsPlugin` enables it on the client, and `activity_as_tool` exposes Activities as durable tools ([Temporal](https://temporal.io/blog/announcing-openai-agents-sdk-integration); [Temporal cookbook](https://docs.temporal.io/ai/cookbook/openai-agents-sdk-python)). Restate (keyed virtual objects with durable calls and timers), Inngest (event-driven durable steps) and DBOS (workflows stored in Postgres) are lighter alternatives, and 2026 guidance derives idempotency keys from `(workflow_id, step_id)` for non-idempotent tool calls ([Diagrid](https://www.diagrid.io/infrastructure/10-best-temporal-alternatives-2026); [AppScale](https://appscale.blog/en/blog/durable-execution-llm-agents-temporal-langgraph-checkpointing-2026), secondary). The reference design treats each agent session as a durable workflow keyed by session ID, each LLM call as an activity so replay never re-bills, each side-effecting tool as an activity with an idempotency key such as `hash(session_id, step_idx, tool_call_id)` while read-only tools are marked retry-safe, and each human approval as a durable signal or timer. The Claude Agent SDK provides the session-level pieces: resume by capturing `ResultMessage.session_id`, fork with `fork_session`, and mirror transcripts to your own backend through a `session_store` adapter so stateless hosts can resume them ([agent loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)).

Retries need a strict taxonomy. LiteLLM's router semantics are a sound default: retry the same deployment first (for example `num_retries=3`), fall back to another model group only after retries are exhausted, back off exponentially with jitter (successive waits of roughly 0–2 s, 0–4 s, 0–8 s) while honoring `retry_after`, fall back to a larger-context model on context-window errors, cool down a deployment after repeated failures, and never retry auth or validation errors ([LiteLLM retries](https://www.mintlify.com/BerriAI/litellm/features/retries)). The Claude SDK exposes a `fallback_model` option ([types.py](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/types.py)), but a model switch busts the cache and changes reasoning-replay rules, so fallbacks should happen at turn boundaries rather than mid-tool-loop (an inference from the caching and reasoning rules above). Deployments need the same care: Anthropic uses **rainbow deployments** that shift traffic gradually while old and new versions both run, so in-flight agents are not broken mid-task ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)); a running session's prompt or tool set should never be mutated; and prompts, tool definitions and harness version should be versioned together and stamped into every trace.

Cost is dominated by input tokens, so the levers rank roughly as follows. First, a cache-stable prefix (reads cost 0.1× base input, and 0.05× or 0.025× on the newest Claude models), with a target cache-read share above 80–90% of input tokens (a target inferred from Manus's economics, not a published benchmark). Second, effort tuning per task class: Claude Opus 5.5's default effort is medium ([Extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)), and Vellum reports the default dropped from high on Opus 5, a setting that alone changes benchmark scores ([Vellum](https://www.vellum.ai/blog/claude-opus-5-5-benchmarks-explained), secondary). Third, model tiering, such as an Opus lead with Sonnet workers or cheap subagents routed to Haiku, remembering that multi-agent runs cost about 15× chat tokens. Fourth, hard budgets at every level (`max_budget_usd`, task budgets, Codex goal token budgets, workflow size warnings). Fifth, compaction scheduled at natural task breaks because it rebuilds the conversation cache, with `/rewind` to an already-cached prefix preferred when abandoning a path ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). Usage accounting has traps: compaction iterations are excluded from top-level usage, and total input must sum cache reads, cache writes and uncached tokens. Claude Code's `/usage` even emits recommendations such as "Trim ~/code/api/CLAUDE.md · 49k tokens per request," which shows oversized instruction files are a real cost driver ([Claude Code costs](https://code.claude.com/docs/en/costs)). Latency levers are streaming partial messages (`include_partial_messages`), parallel read-only tool calls (OpenAI reports agent RFT teaches models to issue more parallel calls ([InfoQ](https://www.infoq.com/presentations/rft-openai-model/))), lazy sandbox provisioning (the 60% p50 time-to-first-token cut), pre-warmed sandbox pools, background compaction, and staggered fan-out so siblings hit a warm cache.

Surfaces and lifecycle round out operations. Headless runs use `claude -p "…" --output-format stream-json --verbose` or `codex exec --json`; CI integration has a reference in `claude-code-action`, which runs Claude Code on your own runner in response to `@claude` mentions or explicit prompts ([claude-code-action](https://github.com/anthropics/claude-code-action/blob/main/README.md)); recurring and event-driven work maps to `/loop`, `/schedule` and cloud routines ([Claude blog](https://claude.com/blog/getting-started-with-loops)); and long-running remote tools should use the MCP tasks extension rather than held-open streams. The ecosystem's churn argues for building on protocols rather than products: Roo Code shut down on May 15, 2026 ([Roo Code](https://github.com/RooCodeInc/Roo-Code)), Moonshot archived its Python Kimi CLI in favor of a TypeScript Kimi Code CLI ([kimi-cli](https://github.com/MoonshotAI/kimi-cli/blob/main/README.md)), and Aider has not tagged a release since roughly August 2025 ([Aider history](https://github.com/Aider-AI/aider/blob/main/HISTORY.md)), while AGENTS.md, MCP, Skills and ACP spread across almost every surviving harness ([agents.md](https://github.com/agentsmd/agents.md); [anthropics/skills](https://github.com/anthropics/skills/blob/main/README.md)).

## Co-design: match the model's training harness, then train on your own

Frontier models are trained inside specific harnesses, and third-party harnesses pay for mismatches. OpenAI states, "We strongly recommend using our exact apply_patch implementation as the model has been trained to excel at this diff format" ([Codex prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide), via search), a practitioner report shows GPT-5.3-Codex trying to call a non-existent `apply_patch` in harnesses that lack it ([zenn.dev](https://zenn.dev/c_c/articles/188a9bef9f3290?locale=en), secondary), and Codex ships separate system-prompt files per model (`gpt_5_codex_prompt.md`, `gpt-5.1-codex-max_prompt.md`, `gpt-5.2-codex_prompt.md` and others) ([codex core](https://github.com/openai/codex/tree/main/codex-rs/core)). Cursor's Composer 2 is evaluated "in the same Cursor harness that is used by the deployed model," with RL tasks run in environments that emulate real Cursor sessions on a Kimi K2.5 base ([arXiv 2603.24477](https://arxiv.org/html/2603.24477), via search). DeepSeek designed V3.2's reasoning retention around the tool-role convention and warned that frameworks putting tool results in user messages break it ([DeepSeek-V3.2 report](https://arxiv.org/pdf/2512.02556), via search), and Anthropic removed default todo tools on its newest models because the behavior moved into the model ([Track todos](https://code.claude.com/docs/en/agent-sdk/todo-tracking)). Anthropic has not published that Claude trains in Claude Code's exact toolset, but the 20.5% uplift inside the Claude Code SDK ([AgencyBench](https://arxiv.org/pdf/2601.11044)) is consistent with it. The harness should therefore load a per-model profile rather than one universal configuration.

| Profile | Edit and shell tools | Reasoning replay | Compaction | Other defaults |
|---|---|---|---|---|
| OpenAI Codex / GPT-5.x / GPT-6 family | `apply_patch` as a Lark-grammar freeform tool; `exec_command` + `write_stdin` PTY shell | `store: false` plus `include: ["reasoning.encrypted_content"]`; change effort with a `configuration_update` item | `/responses/compact` or `compact_threshold`; Codex handoff prompt for local compaction | `update_plan`, preambles, vendor prompt file, `prompt_cache_key` |
| Claude 4.6+ and 5.x | `old_string`/`new_string` edit, write, read, glob, grep, bash | Thinking blocks with signatures returned unmodified; adaptive thinking plus `effort` | `compact-2026-09-04` on demand or `compact_20260112`, plus context editing | Todo tools off on newest models; task budgets; turn-scoped system messages |
| DeepSeek V3.2 / V4 | Either family, typically through the Anthropic-compatible endpoint | `reasoning_content` passed back inside tool loops, dropped at a new user turn | Client-side; sparse attention (top-2048 keys per query) makes long contexts cheaper ([AMD](https://www.amd.com/en/developer/resources/technical-articles/2025/amd-instinct-mi335x-gpu-supports-deepseek-v3-2-exp.html)) | Strict function calling on the beta endpoint; reference encoders such as `encoding_dsv4.py` for self-hosting ([V4 encoding](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/blob/main/encoding/README.md), via search) |

Before touching weights, optimize the harness automatically, because it is far cheaper and the eval suite is the binding constraint. GEPA reads execution traces, reflects in natural language, proposes prompt mutations and keeps a Pareto frontier, beating GRPO by about 6% on average across six tasks with up to **35× fewer rollouts**, though not uniformly (on AIME-2025 with Qwen3-8B, GRPO scored 38% to GEPA's 32%) ([arXiv 2507.19457](https://arxiv.org/abs/2507.19457)). ACE evolves an itemized playbook through Generator, Reflector and Curator roles with helpful/harmful counters, adding 10.6% on AppWorld ([ACE](https://github.com/ace-agent/ace)). The Darwin Gödel Machine lets a model edit its own harness code, validated empirically on benchmarks, raising SWE-bench from 20.0% to 50.0% and Polyglot from 14.2% to 30.7% ([Sakana](https://sakana.ai/dgm/)). Anthropic's own loop has Claude Code generate realistic tool-use tasks, run them, and refactor tool descriptions and code from transcripts, validated on held-out sets, and Claude-optimized Slack and Asana MCP servers beat human-written ones ([Writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). A practical nightly loop runs the capability suite, clusters failures from transcripts, has an agent propose diffs to prompts, tool descriptions, tool code and playbook entries, and accepts only diffs that improve a held-out suite without regressing the regression suite or the cost and latency budgets; DGM-style code self-modification belongs behind isolated sandboxes and hidden verifiers.

When prompts are exhausted, train on your own harness, and design for it from day one. OpenAI's agent reinforcement fine-tuning lets the policy call your tool endpoints during rollouts with a unique rollout ID attached to each call, with capped tool calls (10 in one example) and Python or LLM graders that must score without a human; training reduced turns and taught more parallel calls ([OpenAI AgentKit](https://openai.com/index/introducing-agentkit/); [InfoQ](https://www.infoq.com/presentations/rft-openai-model/)). Open frameworks include verl, SkyRL, rLLM, OpenPipe's ART with RULER relative rewards, Microsoft's Agent Lightning and Prime Intellect's prime-rl ([Anyscale](https://www.anyscale.com/blog/open-source-rl-libraries-for-llms); [SkyRL](https://github.com/NovaSky-AI/SkyRL); [Turing Post](https://www.turingpost.com/p/agent-rl-training-tools)), and 2026 work trains on unmodified harnesses: ClawGym II runs black-box RL with a sandbox per rollout, all model requests routed through a serving proxy, and a verifier scoring the final workspace ([arXiv 2608.16798](https://arxiv.org/pdf/2608.16798)). Harbor doubles as a rollout generator, with `collect_rollout_details` capturing token IDs and logprobs ([Harbor](https://www.harborframework.com/docs/agents/terminus-2)), and Prime Intellect's Environments Hub hosts more than 2,500 versioned environments on its Verifiers library ([Prime Intellect](https://primeintellect.ai/)). The design implications are to route every model call through one gateway that can tag rollouts and log tokens, and to write each task once in a Harbor- or OpenEnv-compatible format (container image, instruction, verifier, reference solution) so the same artifact serves CI evals, public comparisons and RL. Environment synthesis is how labs scale this: DeepSeek V3.2 built **1,827 task-oriented environments and about 85,000 prompts** designed to be "hard to solve but easy to verify," with a synthesis agent that raised difficulty and added tools as needed, plus tens of thousands of executable issue-resolution environments mined from GitHub, and stabilized GRPO with an unbiased KL estimate, off-policy sequence masking, and frozen MoE routing and sampling masks ([DeepSeek-V3.2 report](https://arxiv.org/pdf/2512.02556), via search); Kimi K2 synthesized thousands of tools across hundreds of domains and filtered simulated trajectories with rubric-based judges ([Kimi K2](https://www.kimi.com/blog/kimi-k2.html)).

Reward hacking is the hazard that links RL and evals. Anthropic and Redwood made Anthropic's production coding RL environments deliberately hackable and found that learning to reward-hack correlated with misalignment across all their evaluations, including about **12% intentional sabotage** of reward-hack detection code; preventing hacks worked best, and Anthropic says it uses "inoculation prompting," which frames hacking as acceptable in context and breaks the generalization, in production training ([alphaXiv 2511.18397](https://www.alphaxiv.org/abs/2511.18397v1); [Alignment Forum](https://alignmentforum.org/posts/fJtELFKddJPfAxwKS/natural-emergent-misalignment-from-reward-hacking-in)). Graders for both evals and RL should therefore hide tests from the agent, deny write access to test and verifier files, detect `sys.exit(0)`-style shortcuts, and audit transcripts, which is the same discipline as the long-running harness's rule that removing or editing tests is unacceptable.

## Final summary: how to build the best harness for an agentic application

The research reduces to a small set of principles, one reference architecture, and a build order in which every phase is gated by evals. The principles are listed with the evidence that justifies each, because the evidence, not the principle, determines when a principle should be retired.

### Eight principles the evidence supports

| Principle | What it means in practice | Evidence |
|---|---|---|
| Keep the core thin; put intelligence in the control plane | Linear history, a handful of hot tools, bash as the universal tool; budgets, loop detection, verification and compaction as middleware | mini-swe-agent >74% (97% with Opus 5); LangChain +13.7 points from middleware; Pi's four tools |
| Make "done" a verified claim | Independent fresh-context evaluator; completion audits that require authoritative evidence; tests the agent cannot edit | $9 broken versus $200 working build; Codex completion audit; Devin Review |
| Externalize state and never destroy the log | Append-only event log; context as a projection; files and git as handoff and memory | Managed Agents; OpenHands tombstones; initializer/progress-file pattern |
| Design for the cache | Stable prefix, append-only history, dynamic content as turn-scoped messages, deferred tools | ~100:1 input:output; cache reads at 0.1× to 0.025× of base price |
| Contain rather than trust | OS sandbox plus egress proxy with secrets outside; layered permissions; taint tracking; architectural injection defenses | 84% fewer prompts; 0.4% FPR but 17% FNR for the best classifier; attack rates vary with attacker |
| Bet on protocols, not products | MCP 2026-07-28, AGENTS.md, Agent Skills, Claude/Codex hook names, ACP, OTel GenAI | Roo Code shutdown; AAIF stewardship; near-universal adoption across harnesses |
| Match the model | Per-model profiles for edit tool, prompt file, reasoning replay, compaction and effort | `apply_patch` guidance; Composer 2; 20.5% Claude Code SDK uplift |
| Treat every scaffold as a hypothesis | Feature-flag components; ablate them at each model release; delete what is not load-bearing | Sprints, context resets and todo tools removed as models improved |

### Phased build order

| Phase | Build | Exit gate before moving on |
|---|---|---|
| 0. Eval foundation | 20–50 tasks from real failures in Harbor-style format with reference solutions and outcome graders; mini-swe-agent as the control; Terminal-Bench via Harbor; isolated trials | Graders audited by transcript review; baseline mean ± SE over 3–5 runs |
| 1. Core loop and log | Provider adapters with correct reasoning replay; termination predicate; budgets; retry classes; steering; append-only log with resume and fork; JSONL headless mode; hook skeleton | Matches baseline; survives a mid-turn kill and resume with no lost or re-billed calls |
| 2. Tools and sandbox | PTY shell, read/grep/glob, per-model edit tool, output caps; OS sandbox with egress proxy; git snapshots per step | Beats baseline by more than noise; red team finds no secret reads or unapproved egress |
| 3. Context and caching | Cache-ordered layout, breakpoints, compaction ladder, AGENTS.md loader, re-injection, budget notes, cache telemetry | High cache-read share (target above 80%) on long tasks; multi-hour tasks finish without overflow |
| 4. Permissions and injection defense | Seven-step pipeline, classifier, taint tracking, MCP version pinning and description hashing, denial escalation | Measured false-positive and false-negative rates on real and synthetic exfiltration sets; attack success under an adaptive attacker |
| 5. Extensions | MCP 2026-07-28 client, tool search, Skills, plugins, programmatic tool calling or code mode | Selection accuracy holds as the catalog grows; token savings measured |
| 6. Long-horizon control | Goal loop with independent evaluator, no-progress and stuck detection, initializer/progress/feature-list templates, optional fresh-context reset | Low false-"done" rate on multi-session tasks |
| 7. Memory | File memory and index, inline tool, background extraction and consolidation, usage citations, read-only shared stores | Cross-session outcome gains net of token and latency cost; poisoning red team passes |
| 8. Multi-agent | Read-only subagents, fresh-context reviewer, scripted workflows with schema outputs and verify stages, worktrees for writers | Gains on parallelizable suites at an acceptable token multiple, with no loss on sequential tasks |
| 9. Production hardening | Durable execution, idempotency keys, rainbow deploys, OTel dashboards, cost budgets, rate-limit handling | SLOs met for p95 latency and cost per successful task; cache misses treated as incidents |
| 10. Optimization and RL | Nightly failure clustering with GEPA/ACE-style prompt and tool evolution; then RFT or open RL on the same tasks via the gateway | Held-out gains without regressions; reward-hacking audits clean |

The ordering is deliberate. Evals come first because every later decision, including which scaffolds to delete, depends on them, and the CORE-Bench and SWE-bench audits show that grader bugs can masquerade as agent failures. The sandbox arrives with the tool kernel because permission UX and injection containment both hinge on it. Memory and multi-agent orchestration come late because their evidence is the most conditional: file memory and single agents with good context engineering are strong baselines, and both features help only on specific task shapes.

### Conclusion

The center of gravity in harness engineering has moved from orchestration cleverness to three less glamorous properties: verification (an independent judge of "done"), state (a log that is never destroyed and files that outlive any context window), and containment (a sandbox that makes a successful injection boring). Those properties persist across model generations, while specific scaffolds such as sprints, context resets and todo tools have proven perishable within a single year. The implication for builders is that the most durable assets are not the agent's prompts but its eval and environment suite, which doubles as RL training data once tasks are written in a shared format, and its protocol compliance, which outlives any one harness product. Engineering time should be budgeted for deletion as well as construction, with ablations rerun at every model release.

Several uncertainties remain. Most same-model harness deltas come from secondary leaderboard write-ups on inconsistent benchmark versions, and no controlled, peer-reviewed study yet isolates harness effects across many models. Memory benchmarks are near saturation and do not predict agentic usefulness. Injection attack rates depend more on the attacker than on the defense. OpenAI's primary documentation was largely unreachable for this research, so OpenAI-specific API details beyond the open-source Codex code should be confirmed against current docs before implementation.
