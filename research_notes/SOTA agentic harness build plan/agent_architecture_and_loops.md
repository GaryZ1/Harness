## Q1. How do Anthropic, OpenAI and DeepSeek structure the agent loop? Turn steps, stop conditions, budgets, interrupts and error recovery

### Takeaway
Every major harness runs the same core loop: sample the model, execute any tool calls, append the results, and sample again. The loop ends when the model returns a response with no tool calls. The differences are in the control plane around that loop: hard budgets (turns, dollars, tokens), automatic compaction or context rollover in the middle of a turn, user steering queued during a turn, Stop hooks and goal evaluators that can veto a stop and re-inject a prompt, retry and backoff policies, and durable event logs so a crashed harness can resume. In 2026 both Anthropic and OpenAI added a second, outer loop. Anthropic's is `/goal`, implemented as a prompt-based Stop hook. OpenAI's is the Codex "thread goal" extension. In both, a separate check decides whether "done" is true before the agent is allowed to stop.

### Cited Findings

**Anthropic: Claude Agent SDK / Claude Code loop (current docs)**
- The SDK "runs the same execution loop that powers Claude Code." It has five steps. (1) Receive the prompt along with the system prompt, tool definitions and history; the SDK yields `SystemMessage` subtype `"init"`. (2) Claude "may respond with text, request one or more tool calls, or both"; the SDK yields one `AssistantMessage` per content block. (3) Execute tools; hooks "intercept, modify, or block tool calls before they run". (4) Repeat "until it produces a response with no tool calls". (5) Yield a final `AssistantMessage`, then a `ResultMessage` carrying the final text, usage, cost and `session_id`. — [Claude Code docs: How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- A "turn" is defined as one pass of model output plus tool execution, with no control returned to the caller. `max_turns`/`maxTurns` counts "each turn with tool calls, plus one for the final text-only response". `max_budget_usd`/`maxBudgetUsd` caps estimated spend. Both default to "No limit". The docs say "Setting a budget is a good default for production agents." — [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- The budget is checked *after* each model response arrives, so spend "can therefore pass the cap by up to the cost of that one response," plus whatever running subagents spend. Subagent spend counts toward the cap. Once the cap is reached, spawning a subagent fails with `Budget limit reached` and background subagents are stopped (Claude Code v2.1.217+). — [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- `ResultMessage.subtype` is the termination enum: `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution` (for example a cancelled request or a crash), and `error_max_structured_output_retries`. Every subtype carries `total_cost_usd`, `usage`, `num_turns` and `session_id`. `stop_reason` reports the model's last stop: `end_turn`, `max_tokens` or `refusal`. After a crash it is `null`. — [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Single-shot `query()` raises an error after yielding an error result. A streaming-input session "stays alive" after an error result. With streaming input, a message still queued when a turn hits max-turns starts a new turn and resets the turn count, but the budget keeps accumulating. — [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Parallel tool execution: "Read-only tools (like `Read`, `Glob`, `Grep`, and MCP tools marked as read-only) can run concurrently. Tools that modify state (like `Edit`, `Write`, and `Bash`) run sequentially." Custom tools default to sequential unless they set `readOnlyHint`. A denied tool call comes back to Claude "as the tool result". — [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Conceptual loop as described to users: "gather context, take action, and verify results. These phases blend together." The harness is "the layer around the model that provides the tools and manages the context the model sees." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Interrupts and steering. "Press `Esc` to stop Claude immediately. The running tool call is canceled." Alternatively, "Type a correction and press Enter without stopping Claude… If Claude is running tool calls, it reads the message as soon as those calls finish, within the same turn." This is mid-turn steering through a queue. — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Guard against compaction thrashing: "If a single file or tool output is so large that context refills immediately after each summary, Claude Code stops auto-compacting after a few attempts and shows an error instead of looping." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Background (Sep 29, 2025): the Claude Code SDK was renamed the Claude Agent SDK because "the agent harness that powers Claude Code" now powers "almost all of [Anthropic's] major agent loops." The loop is stated as "gather context -> take action -> verify work -> repeat", and the design principle is "give your agents a computer". — [Claude blog: Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)

**Anthropic: hosted harness architecture (Managed Agents, Apr 8, 2026)**
- The system is split into three interfaces. **Session** is "an append-only event log". **Harness** is "the loop that calls Claude and routes Claude's tool calls". **Sandbox** is the execution environment. Each can be swapped independently. Tools are dispatched through `execute(name, input) → string`. Sandboxes are created with `provision({resources})`. A crashed harness is replaced via `wake(sessionId)`, then `getSession(id)` resumes "from the last event". Events persist through `emitEvent(id, event)`. `getEvents()` reads positional slices so the brain can "rewind" or re-read context. — [Anthropic Engineering: Scaling Managed Agents](https://anthropic.com/engineering/managed-agents)
- Error recovery: when a sandbox dies, the harness treats it as a tool-call error returned to Claude, "which can choose to retry". The first design kept session, harness and sandbox in one container, so a container failure lost the session. Decoupling made containers disposable ("pets vs. cattle"). Provisioning containers lazily, only when a tool call needs one, cut p50 time-to-first-token by about 60% and p95 by more than 90%. — [Managed Agents](https://anthropic.com/engineering/managed-agents)
- The session log is kept outside the context window because compaction, the memory tool and trimming of old tool results or thinking blocks "are irreversible." The harness may transform fetched events before they enter context, for example to improve the prompt-cache hit rate. — [Managed Agents](https://anthropic.com/engineering/managed-agents)

**OpenAI: Codex CLI / codex-rs (source code, Nov 2026)**
- Blog framing (Jan 23, 2026, by Michael Bolin, first post in a series): after each inference the model either "(1) produces a final response to the user's original input, or (2) requests a tool call". Tool output is fed back into a new prompt. "An agent could decide to make hundreds of tool calls in a single turn," so context management is the agent's responsibility. The prompt is a list of items: developer messages describing the sandbox, plus tool definitions for a shell tool, a plan tool and MCP tools. Inference goes over HTTP to the Responses API. — [OpenAI: Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop) (search snippet only; openai.com was unreachable)
- Actual turn loop (`run_turn` in `codex-rs/core/src/session/turn.rs`). Each iteration clones history, calls `run_sampling_request` (a streamed Responses call), and gets back `SamplingRequestResult { needs_follow_up, last_agent_message }`. Then it computes `needs_follow_up = model_needs_follow_up || has_pending_input`: the model emitted tool calls, or the user queued input mid-turn. It reads the context-window token status, may start async compaction (phase `MidTurn` or `PostTurn`), and if `auto_compaction_enabled && needs_follow_up && (model requested new context window || token_limit_reached || async-compaction candidate ready)` it runs `run_auto_compact` and `continue`s. If `!needs_follow_up` it runs Stop hooks (`run_turn_stop_hooks`). If a hook blocks with a continuation prompt, the prompt is recorded as a new message, `stop_hook_active = true`, and the loop continues. If `should_stop`, it breaks. — [openai/codex core/src/session/turn.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn.rs)
- Retry policy defaults: `DEFAULT_STREAM_MAX_RETRIES = 5`, `DEFAULT_REQUEST_MAX_RETRIES = 4`, `DEFAULT_STREAM_IDLE_TIMEOUT_MS = 300_000`. — [openai/codex model-provider-info/src/lib.rs](https://github.com/openai/codex/blob/main/codex-rs/model-provider-info/src/lib.rs). In `run_sampling_request`, `ContextWindowExceeded`, `UsageLimitReached`, `SessionBudgetExceeded` and `Fatal` are returned without retry. Other stream errors go through `handle_response_stream_error` with backoff, and cancellation surfaces as `CodexErr::TurnAborted`. — [turn.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn.rs)
- Default auto-compaction threshold: `auto_compact_token_limit()` returns `min(configured model_auto_compact_token_limit, context_window * 9 / 10)`, i.e. 90% of the window. — [openai/codex protocol/src/openai_models.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/openai_models.rs)
- Request shape: Codex sends `store: false` and `include: ["reasoning.encrypted_content"]`, so the API is stateless (zero data retention) and the client replays encrypted reasoning items itself. `parallel_tool_calls` is passed through. — [openai/codex core/src/client.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/client.rs); [codex-api responses_websocket.rs](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/endpoint/responses_websocket.rs)
- Loop-control tools the model can call: `new_context` ("Start a new context window. Does not clear, reset, or otherwise affect environment state."), `get_context_remaining` ("Get the remaining tokens in the current context window."), and a `sleep` tool ("Pause execution… The sleep ends early when new input arrives for the active turn"). The handler directory also lists `update_plan`, `request_user_input`, `request_permissions`, `multi_agents`/`multi_agents_v2`, `tool_search`, `unified_exec`, `apply_patch`, `view_image` and `send_message_to_user_async`. — [openai/codex core/src/tools/handlers](https://github.com/openai/codex/tree/main/codex-rs/core/src/tools/handlers)
- Autonomy in the system prompt: "You are a coding agent. Please keep going until the query is completely resolved, before ending your turn and yielding back to the user. Only terminate your turn when you are sure that the problem is solved." The prompt also asks for a short "preamble" before tool calls. — [openai/codex protocol/src/prompts/base_instructions/default.md](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)
- OpenAI's 2026 prompting guidance (bundled snapshot of developers.openai.com) says newer models are "more likely to ask the user a question… This can cause it to stop when the user may expect it to… persist." The recommended prompt: "persist until the user's intended goal is complete… Do not stop at acknowledging capability… proposing a plan, or offering to continue." — [openai/codex …/references/prompting-guide.md](https://github.com/openai/codex/blob/main/codex-rs/skills/src/assets/samples/openai-docs/references/prompting-guide.md)

**OpenAI: Agents SDK run loop**
- `Runner.run()` / `run_sync()` / `run_streamed()`. Each turn: (1) call the LLM; (2) classify the output. A **final output** ("text output with the desired type, and there are no tool calls") ends the loop. A **handoff** switches agent and input, then reruns. **Tool calls** are run, results appended, then the loop reruns. `max_turns` overflow raises `MaxTurnsExceeded` (`max_turns=None` disables it). `error_handlers` keys `"max_turns"`, `"model_refusal"` and `"invalid_final_output"` can return fallback outputs instead of raising. Other options: `tool_not_found_behavior` (default raises `ModelBehaviorError`; may be `"return_error_to_model"`), `ToolExecutionConfig.max_function_tool_concurrency`, and `ModelSettings.timeout` / `ToolTimeoutError`. Conversation state is client-side (`to_input_list()`), in an SDK `session`, in a server `conversation_id`, or in `previous_response_id` chaining; these are mutually exclusive. — [openai-agents-python docs/running_agents.md](https://github.com/openai/openai-agents-python/blob/main/docs/running_agents.md)

**DeepSeek (V3.2 thinking-with-tools)**
- The V3.2 tech report specifies thinking-context management for tool loops. Historical reasoning content is discarded **only when a new user message arrives**. Appending tool outputs keeps it, and tool calls and results always stay in context. Copying R1's approach of discarding at the second round "wasted" tokens. The report warns that frameworks which simulate tool calls through user messages (it names Roo Code and Terminus) will trigger the discard. — [DeepSeek-V3.2 tech report, arXiv 2512.02556](https://arxiv.org/pdf/2512.02556) (via search snippet; arXiv unreachable); consistent with [Cline blog](https://cline.bot/blog/deepseek-v3-2-and-v3-2-speciale-are-now-available-in-cline)
- API: thinking mode "supports tool calls. Before outputting the final answer, the model can perform multiple turns of reasoning and tool calls." The official sample appends `content`, `reasoning_content` and `tool_calls` to history. Per a third-party summary of the docs, tool-loop requests must pass `reasoning_content` back "otherwise, the API returns 400". — [DeepSeek API docs: Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/) (snippet); [Tabbit summary](https://go.tabbit.ai/model/deepseek-v3-2/prompts/deepseek-official-thinking-tool-calls-multi-turn-state) (secondary)
- V3.2-Speciale (high-compute) did not support tool calling. — [SGLang cookbook](https://cookbook.sglang.io/autoregressive/DeepSeek/DeepSeek-V3_2)

### Inferences
- A production loop should use this canonical termination predicate: `stop ⇔ (no tool calls in last response) ∧ (no pending user input) ∧ (Stop-hooks/goal-evaluator allow stop)`. Codex's `needs_follow_up = model_needs_follow_up || has_pending_input` plus Stop hooks, and Claude Code's queued-message plus Stop-hook behavior, both implement this.
- Budgets should be enforced in three layers: per-run turns, cumulative dollars or tokens (checked post-response, so leave headroom), and wall-clock or idle timeouts for streams (Codex: 300 s idle). Errors should be split into retryable (transient stream or network: about 4–5 retries with backoff) and terminal (context overflow after compaction failed, auth, credit or usage limits, budget exceeded). Both labs make this split.
- Reasoning state must be replayed correctly within a tool loop. That means Anthropic thinking blocks with signatures, OpenAI encrypted reasoning items (`store:false` plus `include`), and DeepSeek `reasoning_content`. Tool results must go back in the native tool-result role, never as user messages; DeepSeek explicitly drops reasoning on user messages.
- Keep the durable event log separate from the context window (the Managed Agents session). This is what makes crash-resume, rewind, fork and non-destructive compaction possible.

## Q2. Workflow patterns vs autonomous agents: when each is recommended

### Takeaway
Anthropic's December 2024 taxonomy is still the reference vocabulary: prompt chaining, routing, parallelization, orchestrator-workers and evaluator-optimizer are workflows, distinct from autonomous agents. 2026 practice puts these patterns *inside* an agent harness rather than choosing between them. Planner, generator and evaluator agents are wrapped around the core loop, `/goal` adds an evaluator to any loop, and loop types are classified by their trigger (turn, goal, time, event). Labs also say to re-test every such scaffold against each new model and remove the parts that are no longer load-bearing.

### Cited Findings
- (Background, Dec 19, 2024) Workflows are "systems where LLMs and tools are orchestrated through predefined code paths". Agents are "systems where LLMs dynamically direct their own processes and tool usage." The advice is to "find the simplest solution possible, and only increasing complexity when needed." — [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- When to use each pattern, from the same post. **Prompt chaining** suits fixed subtask decomposition, with programmatic gates between steps; "trade off latency for higher accuracy". **Routing** suits distinct input categories that can be classified accurately, for example sending easy queries to smaller models. **Parallelization** comes in two forms: *sectioning* runs independent subtasks such as a guardrail call alongside a response call, and *voting* runs the same task several times when "multiple perspectives or attempts are needed". **Orchestrator-workers** fits when you "can't predict the subtasks needed", such as multi-file code changes. **Evaluator-optimizer** fits when criteria are clear and iteration "provides measurable value". — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Autonomous agents are "typically just LLMs using tools based on environmental feedback in a loop". They need "ground truth from the environment" at each step, may pause at checkpoints for human feedback, and should use stopping conditions such as "a maximum number of iterations". Three principles: simplicity, transparency (show planning steps), and a carefully crafted agent-computer interface (ACI). One poka-yoke example: requiring absolute file paths eliminated a class of errors in SWE-bench runs. — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- (Mar 24, 2026) A GAN-inspired **generator/evaluator** pattern used for frontend design: four criteria (design quality, originality, craft, functionality), few-shot-calibrated evaluator, Playwright MCP screenshots, 5–15 iterations, runs up to 4 hours. The full-stack version uses a **planner → generator → evaluator** three-agent harness with "sprint contracts", in which generator and evaluator agree before coding on what "done" means and how it will be verified. Each criterion has a hard threshold. Agents communicate through files. — [Anthropic: Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Self-evaluation bias: "tuning a standalone evaluator to be skeptical" was easier than making the generator self-critical. Even so, out of the box the evaluator "talked itself out of real issues" and needed several rounds of tuning based on log review. — [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- (Jun 30, 2026) Loop taxonomy from "Loop engineering". **Turn-based** loops are user-prompted and stop when Claude judges the work done; improve them with verification skills. **Goal-based** loops (`/goal`) stop when "an evaluator model checks the condition each time Claude tries to stop" or max turns is reached; best for verifiable exit criteria. **Time-based** loops (`/loop`, `/schedule`) run on an interval. **Proactive** loops are event- or schedule-triggered with no human in real time, and route routine work to smaller models. The post also recommends: "Start with the simplest solution", make verification quantitative, and "Use a separate reviewer agent with fresh context". — [Claude blog: Loop engineering](https://claude.com/blog/getting-started-with-loops)
- Codex distinguishes a "collaboration mode" called Plan Mode from the `update_plan` checklist tool. Plan Mode allows only non-mutating actions and ends in a `<proposed_plan>` that must be "decision complete" so another agent can implement it. — [openai/codex collaboration-mode-templates/templates/plan.md](https://github.com/openai/codex/blob/main/codex-rs/collaboration-mode-templates/templates/plan.md)
- The OpenAI Agents SDK builds multi-agent routing into the core loop as **handoffs**, a third output class next to final output and tool calls. — [openai-agents-python running_agents.md](https://github.com/openai/openai-agents-python/blob/main/docs/running_agents.md)

### Inferences
- For a harness, the useful framing is a single autonomous loop as the default, with workflow patterns available as composable outer structure: router, plan-mode gate, evaluator gate (Stop hook or goal), and orchestrator (subagents or dynamic workflows). These should be configurable rather than hard-coded, because labs keep removing scaffolds as models improve (see Q4 and Q6).
- Evaluator-optimizer is now the most important workflow pattern for long-horizon work. It appears as Anthropic's evaluator agent and `/goal` evaluator, as Codex's goal "completion audit", and as LangChain's self-verification. The evaluator works best with deterministic or quantitative criteria and fresh context.

### Gaps
- I found no 2025–2026 primary source from OpenAI that updates the workflow taxonomy itself; the practical guide was not reachable. I also found no quantitative head-to-head comparison of the workflow patterns.

## Q3. Planning and reasoning inside the loop: ReAct, plan-and-execute, todo tools, think tool, interleaved thinking, effort controls, reasoning-item passing

### Takeaway
ReAct-style interleaving is now native: models think between tool calls (Anthropic adaptive or interleaved thinking, OpenAI reasoning items, DeepSeek thinking-with-tools), so separate "think" tools and rigid plan-then-execute pipelines matter less. Explicit plan or todo tools still exist (Codex `update_plan`, Claude `TaskCreate`/`TaskUpdate`/`TodoWrite`), but Anthropic now turns them **off by default on its newest models** ("newer models track multi-step work without a written todo list"). Reasoning depth is controlled per request with an `effort` enum (low → max). The hard engineering requirement is replaying reasoning state correctly across tool calls without breaking the prompt cache.

### Cited Findings

**Todo / plan tools**
- Codex `update_plan`: "a short list of 1‑sentence steps (no more than 5-7 words each) with a `status` for each step (`pending`, `in_progress`, or `completed`)". "There should always be exactly one `in_progress` step until everything is done." If the plan changes mid-task, the model calls `update_plan` with an `explanation`. "Do not repeat the full contents of the plan after an `update_plan` call — the harness already displays it." — [openai/codex base_instructions/default.md](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)
- In Codex Plan Mode, calling `update_plan` returns an error, which keeps the planning mode and the progress tool separate. — [codex plan.md](https://github.com/openai/codex/blob/main/codex-rs/collaboration-mode-templates/templates/plan.md)
- Claude Code: `TodoWrite`, `TaskCreate`, `TaskGet`, `TaskUpdate` and `TaskList` are available by default "only on Claude Opus 4.7, Claude Sonnet 4.6, Claude Haiku 4.5, and earlier models". On newer models they are opt-in (`CLAUDE_CODE_ENABLE_TODO_TOOLS=1`, or list them in `allowedTools`). The docs say: "Newer models track multi-step work without a written todo list." Lifecycle: `pending` → `in_progress` → `completed`, with `status: "deleted"` to remove an item. Todos are used for tasks with "three or more distinct actions" (applies from Claude Code v2.1.268). — [Claude Code docs: Track todos](https://code.claude.com/docs/en/agent-sdk/todo-tracking)
- The Codex goal continuation prompt says: use `update_plan` "if… the next work is meaningfully multi-step… Skip planning overhead for trivial one-step progress, and do not treat a plan update as a substitute for doing the work." — [codex ext/goal/templates/goals/continuation.md](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/continuation.md)

**Think tool (background) and interleaved / adaptive thinking**
- (Mar 20, 2025) The "think" tool on τ-bench airline: pass^1 rose from 0.370 to 0.570 with an optimized prompt, a 54% relative gain. Retail rose from 0.783 to 0.812. A similar tool contributed to Claude 3.7 Sonnet's 0.623 on SWE-bench. — [Anthropic: The "think" tool](https://www.anthropic.com/engineering/claude-think-tool) (figures via search snippet of the primary page). A secondary source says Anthropic now recommends extended or adaptive thinking over a separate think tool in most cases. — [agentpatterns.ai](https://agentpatterns.ai/patterns/agent-design/think-tool/) (secondary, unverified)
- Interleaved thinking "lets Claude think between tool calls within a single assistant turn." On Opus 4.5, Sonnet 4.5 and earlier Claude 4 models it needs the `interleaved-thinking-2025-05-14` beta header. Adaptive thinking (`thinking: {type: "adaptive"}`) "interleaves automatically". Manual `type: "enabled"` with `budget_tokens` is deprecated: "Claude 4.7 and later models… reject requests that use it, returning a 400 error." Migration: drop `budget_tokens`, set `thinking: {type: "adaptive"}`, and use `output_config: {effort: ...}`. — [Anthropic docs: Extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)
- Thinking-block preservation: "Claude Opus 4.5 and models numbered 4.6 and higher keep prior turns' thinking blocks in context and bill them as input," whereas Sonnet 4.5, Haiku 4.5 and earlier strip them. Changing `budget_tokens` or switching thinking mode invalidates prompt-cache breakpoints, so "pick a budget and hold it stable for the life of a cached conversation." The docs demonstrate a full re-creation of a 1,370-token cache after a budget change. — [Extended thinking docs](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)
- Effort defaults: Opus 5.5 and Haiku 5.5 default to `"medium"`; other effort-capable models default to `"high"`. — [Extended thinking docs](https://platform.claude.com/docs/en/build-with-claude/extended-thinking). The Agent SDK `effort` levels are `"low"`, `"medium"`, `"high"`, `"xhigh"` and `"max"`, settable per session or per subagent (`AgentDefinition.effort`). Effort is independent of thinking display. — [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)

**OpenAI reasoning controls and reasoning items**
- Codex requests `include: ["reasoning.encrypted_content"]` with `store: false`, so reasoning items persist across turns through client-side replay of encrypted content. — [codex core/src/client.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/client.rs)
- The GPT-6 guidance bundled in the Codex repo lists `reasoning.effort` values `low`, `medium` (default), `high`, `xhigh` and `max`. Astra and 6.1 Sol do not support `none`; Sol and Luna do. To change effort *mid-conversation without breaking the cache*, add a `configuration_update` input item and "keep request-level `reasoning.effort` unchanged to preserve the prompt prefix for caching." Tool calling with reasoning requires the Responses API. Optional features include "persisted reasoning", "Programmatic Tool Calling", "compaction" and "pro mode". — [codex …/upgrading-to-gpt-6-astra.md](https://github.com/openai/codex/blob/main/codex-rs/skills/src/assets/samples/openai-docs/references/upgrading-to-gpt-6-astra.md) (a bundled snapshot of developers.openai.com; treat as near-primary)
- The Agents SDK's `reasoning_item_id_policy` (`"preserve"` default, or `"omit"`) controls whether reasoning-item IDs are kept in follow-up input. `"omit"` is a mitigation for "Responses API 400 errors caused by a reasoning item that lacks its required following item." — [openai-agents-python running_agents.md](https://github.com/openai/openai-agents-python/blob/main/docs/running_agents.md)

**DeepSeek**
- In V3.2, reasoning is retained across tool calls and discarded only on a new user message. See Q1 for the source. — [DeepSeek-V3.2 report](https://arxiv.org/pdf/2512.02556) (snippet)

**Preambles / transparency**
- Codex instructs the model to send "a brief preamble to the user explaining what you're about to do" before tool calls, grouping related actions. — [codex default.md](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)

### Inferences
- Design for native interleaved reasoning (think → tool → think) and make the todo or plan tool *optional, model-gated configuration*, enabled for weaker or older models and for UI progress rendering. A plan tool's main value is now the UX it gives the user and its persistence across compaction, not the model's own reasoning.
- Treat the reasoning configuration (effort, thinking mode, budget) as part of the cache key. Change effort through in-band items (OpenAI `configuration_update`) or by session or subagent, not per request, to avoid cache misses.
- Keep a separate plan *mode* (a read-only, non-mutating permission state that ends in an approvable plan artifact) apart from the plan *tool*. Codex and Claude Code both do this.

## Q4. Long-running and long-horizon agents: initializer + incremental progress, progress files, git checkpoints, compaction-driven continuation, multi-hour runs, Ralph loops, self-verification, background agents

### Takeaway
Two families of technique have converged. (a) **External-state continuity.** An initializer session writes a feature list (JSON), a progress log, an `init.sh` and a first git commit. Each later fresh-context session reads that state, does one feature, verifies it end to end, commits and logs. Ralph loops are the extreme case: an outer `while true` that re-feeds the same prompt with state carried in files and git. (b) **In-model or in-harness continuity.** Models trained to work across compaction boundaries (GPT-5.1-Codex-Max, Nov 2025) and harness-level goal loops with independent completion audits (Claude Code `/goal`, Codex thread goals with token budgets). Reported runs reach multiple hours (Anthropic: 4–6 hours per app build; OpenAI: more than 24 hours internally). Labs also report that scaffolds built for older models (context resets, sprints) became "dead weight" on newer models.

### Cited Findings

**Anthropic: initializer + coding agent (Nov 26, 2025, by Justin Young)**
- The initializer agent's first session creates `init.sh`, `claude-progress.txt` and an initial git commit. It also writes a JSON feature list; the claude.ai-clone experiment had more than 200 features, all starting as failing, each with `category`, `description`, `steps` and `passes`. Later "coding agents" may change only `passes`. The prompt says: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." JSON was chosen because the model is less likely to inappropriately rewrite it than Markdown. The two agents differ *only in the initial user prompt*; system prompt, tools and harness are identical. Model: Opus 4.5 on the Claude Agent SDK. — [Anthropic: Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Coding-session start ritual: (1) `pwd`; (2) read git logs and progress files; (3) read the feature list and pick the highest-priority failing feature; (4) run `init.sh` to start the dev server and run a basic end-to-end test before new work. Sessions work on one feature at a time and end with a commit and a progress update, leaving code "clean" enough to merge. — [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Failure modes and fixes: declaring the project done too early (fix: feature list), leaving bugs or undocumented state (fix: git plus progress notes plus a smoke test at start), marking features done prematurely (fix: test end to end "as a human user would" with Puppeteer MCP), wasting time on startup (fix: `init.sh`). The post says "compaction isn't sufficient" because it "doesn't always pass perfectly clear instructions to the next agent." — [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**Anthropic: planner / generator / evaluator long runs (Mar 24, 2026, by Prithvi Rajasekaran)**
- "Context anxiety": Sonnet 4.5 wrapped up early as it approached its perceived context limit, so **context resets** (a fresh agent plus a structured handoff artifact) were essential. Opus 4.5 "largely removed" the behavior, so resets were dropped in favour of compaction. — [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- RetroForge game maker on Opus 4.5: a solo run took 20 min and cost $9 and produced a broken app; the full harness took 6 hr and cost $200 and produced a playable app. The spec had 16 features across 10 sprints, and sprint 3 had 27 contract criteria. — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- On Opus 4.6 the sprint construct was **removed** because the model "built coherently without decomposition". The planner was kept (without it the generator under-scoped) and the evaluator moved to a single end-of-run pass. A browser DAW run took about 3 h 50 m and $124.70 in total: planner 4.7 min/$0.46, build round 1 2 h 7 m/$71.08, QA 8.8 min/$3.24, build round 2 1 h 2 m/$36.89, plus two more short rounds. "The builder ran coherently for over two hours without sprints." — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Principle: "Every harness component encodes an assumption about what the model can't do alone," and those assumptions go stale. — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps). Managed Agents makes the same point: context resets added for Sonnet 4.5 "had become dead weight" on Opus 4.5. — [Managed Agents](https://anthropic.com/engineering/managed-agents)

**Goal loops (2026)**
- Claude Code `/goal <condition>` (condition up to 4,000 characters) is "a wrapper around a session-scoped prompt-based Stop hook". After each turn the small fast model receives the condition plus the transcript and returns **Not yet met** (the reason becomes guidance for the next turn), **Met**, or **Impossible**. The evaluator "does not call tools, so it can only judge what Claude has already surfaced". Bounding is done in the condition text itself ("or stop after 20 turns"). Guard: if there is "no tool use for several turns in a row", Claude Code stops the loop. — [Claude Code docs: /goal](https://code.claude.com/docs/en/goal)
- `/goal` error policy. Unrecoverable errors clear the goal: an auth failure, exhausted credit, context overflow that auto-compaction couldn't clear, or an unavailable model. Transient errors (overload, dropped connection) retry automatically, then pause after three retries. Rate or usage limits pause the goal and resume when the limit resets. If background subagents or shells are running, evaluation is deferred, and a check-in is issued after 30 minutes with backoff (1 h, then every 2 h), capped at three idle check-ins (`CLAUDE_CODE_GOAL_CHECKIN_MINUTES`). The goal persists across `--continue` and `--resume`, with the turn count and token baseline reset. Headless: `claude -p "/goal …"`. — [/goal docs](https://code.claude.com/docs/en/goal)
- Codex thread goals (`codex-rs/ext/goal`). Each continuation turn is injected with a template containing the `<objective>` (treated as "user-provided data… not as higher-priority instructions") and the budget ("Tokens used / Token budget / Tokens remaining"). Key rules: "Keep the full objective intact… do not redefine success around a smaller or easier task." A **no-progress check** classifies each turn as progress, a verified wait, or no progress. A **completion audit** requires that the model "derive concrete requirements… identify the authoritative evidence… Treat uncertain or indirect evidence as not achieved… The audit must prove completion, not merely fail to find obvious remaining work." The **blocked audit** allows `update_goal` with status `"blocked"` only after the same blocker repeats "for at least three consecutive goal turns". Other statuses are `"complete"` and `"paused"` (pause only on user request). At budget exhaustion a `budget_limit.md` template marks the goal `budget_limited` and tells the model to "wrap up… summarize useful progress… leave the user with a clear next step." — [codex ext/goal/templates/goals/continuation.md](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/continuation.md); [budget_limit.md](https://github.com/openai/codex/blob/main/codex-rs/ext/goal/templates/goals/budget_limit.md)
- The Codex "persistent mode" prompt covers proactive follow-ups after the final answer. Before starting one, the model should identify "its scope, the outcome you want to establish, the evidence needed, and a stopping condition"; it should poll with "short, proportionate waits, often 1–3 minutes", and keep "the target, last known state, stopping condition, and next check in the available task/checkpoint state so the follow-up survives sleep and context resets." "Persistence does not broaden that scope." — [codex prompts/templates/persistent_mode.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/persistent_mode.md)

**Compaction-driven continuation**
- Codex compaction prompt: "You are performing a CONTEXT CHECKPOINT COMPACTION. Create a handoff summary for another LLM that will resume the task", covering progress and decisions, constraints and preferences, remaining next steps, and critical data. The summary is re-inserted with the prefix "Another language model started to solve this problem and produced a summary of its thinking process…" — [codex prompts/templates/compact/prompt.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/compact/prompt.md); [summary_prefix.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/compact/summary_prefix.md)
- GPT-5.1-Codex-Max (Nov 19, 2025) was OpenAI's first model "trained to run across several context windows via compaction" and can work "over millions of tokens on one task". OpenAI observed it working on tasks for more than 24 hours in internal evaluations. — [OpenAI: GPT-5.1-Codex-Max](https://openai.com/index/gpt-5-1-codex-max/) (search snippet; openai.com unreachable)
- The Claude Agent SDK compacts automatically near the limit and emits `SystemMessage` `subtype: "compact_boundary"`. A `PreCompact` hook (trigger `manual` or `auto`) can archive the transcript. Compaction instructions can live in CLAUDE.md, because "CLAUDE.md content is re-injected on every request" while early instructions in the prompt may be lost. — [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)

**Ralph Wiggum outer loops**
- Anthropic's official `ralph-loop` plugin. Huntley's original: "Ralph is a Bash loop", a `while true` that re-feeds a prompt file. The plugin instead runs it inside a session with a **Stop hook** that blocks exit and feeds the *same* prompt back, so "Claude's previous work persists in files" and git. Usage: `/ralph-loop "<prompt>" --max-iterations <n> --completion-promise "<text>"`, cancel with `/cancel-ralph`. State lives in `.claude/ralph-loop.local.md` (frontmatter `max_iterations`, `completion_promise`, `session_id`). The hook reads the last assistant text block from `transcript_path` and looks for `<promise>…</promise>`. — [anthropics/claude-plugins-official plugins/ralph-loop](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop)
- Stop-hook safety cap: "Claude Code overrides a Stop hook after it blocks eight times in a row with no tool call from Claude in between". Scripts should check `stop_hook_active` and exit early if it is true. — [Claude Code docs: hooks guide](https://code.claude.com/docs/en/hooks-guide)

**Reported durations / horizons (mostly secondary)**
- Opus 4.5 50% time horizon "about 4 hours and 49 minutes"; 80% horizon 27 minutes (METR-style, via 36Kr). — [36Kr](https://eu.36kr.com/en/p/3605865159247104) (secondary). Opus 4.6 (Feb 5, 2026) at a reported 14.5-hour 50% horizon. — [MindStudio](https://www.mindstudio.ai/blog/claude-opus-4-6-autonomous-task-horizon-14-5-hours) (secondary, unverified)
- Anthropic engineering posted "Building a C compiler with a team of parallel Claudes" (Feb 5, 2026). — [Anthropic Engineering index](https://www.anthropic.com/engineering) (title and date only; not read)

### Inferences
- A production harness should provide all three continuity mechanisms: (1) in-loop compaction at about 90% of the window, with a handoff-style summary prompt and a durable full log; (2) an optional "fresh context" or `new_context` tool or reset mode for models that show context anxiety; (3) an outer goal loop with an *independent* evaluator, a no-progress detector, a blocked-after-N-repeats rule, token or time budgets, and retry, pause and clear semantics by error class.
- External-state artifacts (a JSON feature list with immutable test definitions, a progress log, `init.sh`, git commits per unit of work, a smoke test at session start) are a cheap, model-agnostic way to get multi-session reliability. They should be first-class harness templates.
- Every long-horizon scaffold (sprints, resets, todo lists) needs a feature flag and per-model evaluation, since the labs report removing these as models improve.

## Q5. Harness-level features: hooks, permission modes, plan mode, streaming, persistence and resume, checkpoints and rewind, headless/SDK, slash commands, skills

### Takeaway
Claude Code and Codex have converged on almost the same feature surface, down to identical hook event names (`PreToolUse`, `PostToolUse`, `Stop`, `SubagentStop`, `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreCompact`, `PostCompact`, `PermissionRequest`). Hooks are the main extension point for loop control: block a tool, rewrite its input, veto a stop, inject context. Permission modes now include a model-classifier "auto" mode as the default. Sessions are append-only JSONL or event logs that support resume and fork, and file checkpoints are separate from git.

### Cited Findings

**Hooks**
- Claude Code hook events (lifecycle order) include `SessionStart`, `Setup`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Notification`, `SubagentStart`/`SubagentStop`, `TaskCreated`/`TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `FileChanged`, `WorktreeCreate`/`WorktreeRemove`, `PreCompact`/`PostCompact`, `PreModelSwitch`/`PostModelSwitch`, `Elicitation`/`ElicitationResult` and `SessionEnd`. Hook types are `command`, `http`, `mcp_tool`, `prompt` (a single-turn LLM decision) and `agent` (a subagent with tools; experimental; up to 50 tool-use turns). Default timeouts are 600 s for command, http and mcp_tool, 30 s for prompt, and 60 s for agent. — [Claude Code docs: Hooks reference](https://code.claude.com/docs/en/hooks); [hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Control semantics. Exit code `2` is a blocking error and stderr becomes the reason. `PreToolUse` returns `hookSpecificOutput.permissionDecision` ∈ {`allow`,`deny`,`ask`,`defer`} plus `updatedInput`, which rewrites the arguments. A Stop hook can return `{"decision":"block","reason":…}` to force continuation or `{"continue": false, "stopReason": …}` to halt. Stop-hook input includes `last_assistant_message`. Hooks run in-process and "don't consume context". — [Hooks reference](https://code.claude.com/docs/en/hooks); [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- The Codex hooks crate implements the same event names (`PreToolUse`, `PostToolUse`, `Stop`, `SessionStart`, `UserPromptSubmit`, `SubagentStop`, `SessionEnd`, `PreCompact`, `PostCompact`, `PermissionRequest`). Stop hooks can block with "continuation fragments" that are injected as a prompt message. A block with no prompt is ignored with the warning "Stop hook requested continuation without a prompt; ignoring the block." — [openai/codex hooks/src](https://github.com/openai/codex/tree/main/codex-rs/hooks/src); [turn.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn.rs)

**Permission modes / plan mode**
- Agent SDK `permission_mode` values: `"default"` (`canUseTool` callback; no callback means deny), `"acceptEdits"`, `"plan"` (no source edits), `"dontAsk"` (never prompts; anything not pre-approved is denied; for headless use), `"auto"` (a model classifier reviews actions), and `"bypassPermissions"` (isolated environments only; in TypeScript it also needs `allowDangerouslySkipPermissions: true`; it cannot be used as root). Rules can be scoped, for example `"Bash(npm *)"`. — [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Auto mode is "the built-in starting permission mode" for interactive terminal and VS Code sessions from Claude Code v2.1.283. `Shift+Tab` cycles Auto, Manual, Accept edits and Plan. — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works). Anthropic's design post on this is "How we built Claude Code auto mode: a safer way to skip permissions" (Mar 25, 2026). — [Anthropic Engineering index](https://www.anthropic.com/engineering) (not read)
- Codex prompt templates exist for each sandbox mode (`read_only`, `workspace_write`, `danger_full_access`) and approval policy (`never`, `unless_trusted`, `on_request`). A "guardian" classifier policy reviews actions. — [openai/codex prompts/templates/permissions](https://github.com/openai/codex/tree/main/codex-rs/prompts/templates/permissions); [guardian](https://github.com/openai/codex/tree/main/codex-rs/prompts/templates/guardian)

**Sessions, checkpoints, headless**
- Claude Code writes every message, tool use and result to JSONL under `~/.claude/projects/`. `--continue`/`--resume` reopen the same session ID, and `--fork-session` or `/branch` copy history into a new ID. Before editing, Claude snapshots files; "press `Esc` twice to rewind". Checkpoints are "separate from git" and cannot undo remote side effects. — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- SDK: capture `ResultMessage.session_id` to resume. A `session_store`/`sessionStore` adapter mirrors transcripts to your own backend so stateless hosts can resume them ("dual-write"). The streaming option `include_partial_messages` yields `StreamEvent` text and tool-input deltas. — [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Headless: `claude -p "…"`, with `--output-format stream-json --verbose` for incremental events. — [/goal docs](https://code.claude.com/docs/en/goal)

**Skills and slash commands**
- Skills load progressively: "Claude sees skill descriptions at session start, but the full content only loads when a skill is used". `disable-model-invocation: true` keeps a skill's description out of context. — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works). Agent Skills launched Oct 16, 2025. — [Anthropic Engineering index](https://www.anthropic.com/engineering)
- Codex ships a `skills` crate with bundled sample skills, and `mcp_skill_dependencies`, which shows OpenAI adopted the SKILL.md skills model in Codex. — [openai/codex codex-rs/skills](https://github.com/openai/codex/tree/main/codex-rs/skills)
- In the SDK, slash commands such as `/compact` are sent "as a prompt string", i.e. as ordinary inputs. — [agent-loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Scheduling surfaces: `/loop` runs locally at an interval, `/schedule` and "routines" run in the cloud on cron, API or GitHub events, and "dynamic workflows" orchestrate many subagents from a rerunnable script Claude writes. — [Loop engineering](https://claude.com/blog/getting-started-with-loops); [Claude Code docs index](https://code.claude.com/docs/llms.txt)

### Inferences
- Minimum viable hook contract for a new harness: pre-tool (allow, deny, ask, rewrite), post-tool (audit or inject), stop (block plus reason, or halt), pre-compact, session start/end, and subagent stop, with exit-code and JSON semantics compatible with Claude Code and Codex. The two are already near-identical, so matching them gives free ecosystem compatibility.
- The stop-hook block cap (8 consecutive blocks with no tool call) and Codex's ignore-on-empty-prompt rule are necessary guards against runaway outer loops.

## Q6. Evidence that "the harness matters as much as the model": benchmark deltas, minimal-harness arguments, model–harness co-design

### Takeaway
Harness choice moves agentic benchmark scores by roughly 3–14 points with the model held fixed. The strongest documented case is LangChain: 52.8% → 66.5% on Terminal-Bench 2.0 with the same GPT-5.2-Codex, from harness changes only. At the same time, minimal harnesses are competitive: mini-swe-agent uses about 100 lines and only bash, and scores above 74% on SWE-bench Verified with frontier models. Both observations point the same way. Frontier models are post-trained *inside their own harnesses* (Codex, Cursor Composer, Windsurf SWE-1.5), so the harness and model are co-designed and harness wins are partly a matter of matching the training distribution. Labs keep pruning harness components that new models no longer need.

**Model–harness co-design**
- GPT-5.1-Codex-Max was "trained to run across several context windows via compaction". — [OpenAI GPT-5.1-Codex-Max](https://openai.com/index/gpt-5-1-codex-max/) (snippet). Secondary coverage of OpenAI's "harness engineering" post notes that "Codex models are trained in the presence of the harness". — [search coverage of openai.com/index/harness-engineering](https://openai.com/index/harness-engineering/) (unverified snippet). The Codex repo ships model-specific system prompts (`gpt_5_codex_prompt.md`, `gpt-5.1-codex-max_prompt.md`, `gpt-5.2-codex_prompt.md`, `gpt_5_1_prompt.md`, `gpt_5_2_prompt.md`), which shows prompts are tuned per model. — [openai/codex codex-rs/core](https://github.com/openai/codex/tree/main/codex-rs/core)
- Cursor Composer 2 is evaluated "in the same Cursor harness that is used by the deployed model, with equivalent tools and structure". Its RL tasks "run in environments that emulate real Cursor sessions", and the base model is Kimi K2.5 (1.04T total / 32B active MoE). — [Cursor Composer 2 technical report, arXiv 2603.24477](https://arxiv.org/html/2603.24477) (snippet). Composer 1 was RL-trained in a harness that simulated Cursor's production tools. Windsurf SWE-1.5 was RL-trained in its own Cascade harness. — [Simon Willison, Oct 29, 2025](https://simonwillison.net/2025/Oct/29/) (snippet)
- DeepSeek's V3.2 report explicitly designs thinking retention around agent-framework conventions (tool role vs user role) and notes the incompatibility with frameworks that put tool results in user messages. That is co-design from the model side. — [DeepSeek-V3.2 report](https://arxiv.org/pdf/2512.02556) (snippet)
- Anthropic stopped providing todo tools by default on newer models. This is a harness component removed because the model internalized the behavior. — [Track todos](https://code.claude.com/docs/en/agent-sdk/todo-tracking)

### Inferences
- For a new harness, the evidence supports a **thin core** (mini-swe-agent-style: a linear history, a few general tools, bash or exec as the universal tool) plus **thick, optional control-plane middleware**: verification gates, loop and no-progress detection, time and token budget warnings, compaction, and goal evaluators. Measured gains come mostly from the second category (LangChain's middleware, Anthropic's evaluator, the goal audits).
- Because frontier models are post-trained in their vendors' harnesses, a third-party harness gets the best results by matching vendor conventions: tool names and shapes (`apply_patch`/`update_plan` for OpenAI; `Read`/`Edit`/`Bash`/`TodoWrite`-style for Anthropic), vendor system-prompt files, and correct reasoning-state replay. Supporting a per-model prompt and tool profile is likely worth several benchmark points.
- Harness benchmark claims should be treated with caution unless the model is held fixed, the same benchmark version is used (TB 2.0 vs 2.1 differ), and infrastructure noise is controlled.

### Gaps
- tbench.ai, snorkel.ai and blog.langchain.com were unreachable, so all Terminal-Bench harness deltas here are secondary and partly inconsistent: Snorkel reportedly lists Claude Code + Fable at 83.8% where the blog cited above has 83.1%.
- I found no controlled, peer-reviewed 2025–2026 study isolating harness effects across many models. The arXiv "agent harness survey" ([Preprints.org 202604.0428](https://www.preprints.org/manuscript/202604.0428)) was found but not read. I found no primary OpenAI or Anthropic statement quantifying harness-only deltas on SWE-bench.
